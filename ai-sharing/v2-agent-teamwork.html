背景

复盘对象与 20 天总账

  • dsh-plugin-hub：DSH Web GUI 插件集（8 个插件 + 聚合包），npm 公开发布，6.1 万行 TS
  • 20 天：392 commits / 287 PR / 221 issues / 14 个发版（v0.1.0 → v0.2.1）
  • 人的角色：提需求、定方向、审方案、批红线——20 天里我没有直接写过一行仓库里的代码
  • AI 的角色：规格起草、编码、测试加固、代码清理、QA 验收、维护编排——全链路

为什么这个案例值得看

它不是 demo 项目：有真实用户、公开 npm、事故会真实发生（SSE 泄漏当天紧急发版）。管理体系的好坏会被市场直接打分——这是检验 AI 协作方法论最诚实的环境。

强调「人没写代码」这个事实，制造第一波张力。但立刻补一句：人做的事变难了，不是变少了——为全场定调。
01 体系设计的出发点

为什么不是「让 AI 随便写」

  • AI 写码的三大天性：过度自信（说改好了但没验证）、上下文短视（不知道系统里还有谁）、服从表象（规范写在文档里约等于不存在）
  • 无管理的结果在第一天就见过：功能能跑、生命周期泄漏、Windows 全炸
  • 结论：把 AI 当高产能初级工程师团队来管理——而管理初级团队靠的不是信任，是流程 + 权限 + 验收

体系设计的三个公理

① 不信任单点输出：任何 agent 的产出都要有独立检查
② 权限跟着风险走：低风险自动放行，高风险人批
③ 一切凭据留痕：状态、证据、决策全部写进 issue，不靠会话记忆

这页给出全场理论框架。用公司场景类比：你会让一个实习生直接往 main 推代码、直接发版吗？不会——那为什么对 AI 会？

  • 每个角色一张「岗位说明书」（agents/*.md + 公共协议 _protocol.md）：职责边界、输入输出、禁止事项
  • 关键设计：角色间不共享对话记忆，交接全靠仓库内的书面凭据（issue / PR / 规格）
对照公司组织：主控=技术负责人，编排层=PMO/流水线，角色层=职能团队。指出最大差异：agent 角色切换零成本，所以「分角色」几乎免费——这是 AI 组织独有的红利。
02 组织设计

岗位说明书长什么样

角色职责关键约束
spec-writer把 issue 转成可执行规格只写规格不写码；规格含验收判据
coder按规格实现 + smoke 断言禁越权改公共 API / 依赖
cleaner去重 / 死代码 / 收敛 shared禁改行为——只许等价重构
hardener边界 / 错误路径 / 安全加固禁顺手加功能
qa（兼 judge）按规格判据独立验收与实现角色隔离；判据不含糊
  • 公共协议约定：遇阻塞不绕路，把阻塞原因写进返回值由主控升级——禁止 agent 自行「创造性解决」越权问题
  • 效果类比：初级工程师最危险的不是不会，是「顺手把问题绕过去」——协议把它堵死
讲一个真实细节：cleaner「禁改行为」这类负面约束比正面描述更重要——agent 的越权行为几乎都发生在「好心办坏事」：重构时顺手优化、修 bug 时顺手加功能。
03 流程

工作流：issue 驱动的状态机

CLAIM认领从 zone/auto 队列取 issue
WORKTREE隔离独立 worktree，主 checkout 永远干净
SPEC规格spec-writer 产出规格 + 判据
IMPL实现coder + smoke 断言
QA复核qa 按判据验收 + 计圈收敛
MERGE合并门禁全绿 → auto-merge → 清理
  • 计圈收敛环：qa 打回算一圈，同 issue 超过设定圈数自动升级给主控——防止 agent 在死循环里空转烧钱
  • 转向检查：每轮循环检查 maintainer 在 PR/issue 里的新评论，有人话就先听人话
  • 细粒度状态走 issue 内格式化状态行（[loop] ts=…），粗粒度走标签——会话会死，issue 永存
重点讲计圈机制：它回答「AI 失控时怎么发现」——不是靠人盯，是让流程自己暴露异常（圈数是噪音指标）。转向检查则是人机之间的免打断通道。
03 流程

授权标签体系：AI 的权限带宽

zone/autoapprovedapi-approved pending-ratification zone/red-lineblocked-humanneeds-proposal-review

  • zone/auto：AI 可全流程自治（修 bug、内部重构、测试加固）——但门禁一个不减
  • zone/red-line：公共 API 行为变更、新依赖、CI/workflow、发版——必须在原 issue 出方案，人工 approved 后才许动手
  • priority/critical 紧急通道：跳决策直进实施，门禁不减，合并后 24 小时内人工追认
  • 铁律：「按此执行」只授权 AI 代打 zone 标签；approved / api-approved 永不代打

设计原则

不是「AI 能不能做」的问题，是「AI 做了之后谁能追责」的问题。标签体系就是审计日志 + 权限模型的合体：每个标签谁打的、什么时候打的，仓库里可查。

用公司治理类比：zone/auto=授权审批额度内自主，red-line=上会。强调「永不代打」——这是防止权限提升攻击（AI 自己打 approved 然后自己合并）的关键一环。
03 流程

方案门：把「先讨论再动手」制度化

  • 高风险改动动手前，agent 必须先在原 issue 内起草方案评论，打 needs-proposal-review
  • 复杂方案还要拉独立子 agent 做对抗性评审：正确性/边界/性能/安全/兼容性/是否过度设计……
  • 子 agent 与方案作者不带共享上下文——评审者没有先入之见，才挑得出真错
  • 获批后返回主控定去向，不单开决策 issue——决策与实施同源，审计链完整

实测效果

20 天里靠方案门拦截的典型错误：依赖选型重复造轮子（后改为强制先调研开源库）、覆盖率口径虚高（vendor 混入）、变异区间手写漂移（后改自动派生）。

方案阶段纠错成本 ≈ 0；合并后纠错成本 = 一个紧急发版。

对抗评审是全场最能借鉴的实践之一：让另一个无上下文的 agent 只读方案文档挑错，专治「自己审自己越审越满意」。成本极低，收益极高。
04 上下文工程

上下文是 AI 组织的第一资源

  • 注入纪律：注入上下文曾经过度频繁，被用户抱怨（#457）——纪律文本本身要做「信息密度治理」（#414）
  • MCP 中间层收敛：项目级 MCP 工具收敛为 ws_mcp_search/ws_mcp_call 两个原子工具——接入 20 个 MCP 不再膨胀 20 份 schema（#312/#413）
  • 结构化查询代替全文搜：codegraph 工具层强制「查询前 sync」，查询纪律写进注入文本（#329/#363）
  • 可见性要诚实：ws_mcp_list 过滤无命中曾谎报「未配置」——对 agent 撒谎会导致连环误判（#362）

视角转换

管理人类团队时稀缺资源是注意力；管理 agent 团队时稀缺资源是上下文窗口。一切「会议」（注入文本）都要按信息密度付费——冗长纪律 = 挤占有效工作记忆。

这章是 v2 相对 v1 的差异化内容。「ws_mcp_list 谎报未配置」这个案例很妙：对人类，文档错误是困惑；对 agent，工具返回的错误描述会被当成事实并执行下去。
05 失败与迭代

失败案例一：协作体系自己的第一轮复盘

  • 20260822 维护轮跑完后，主控复盘出 七项改进（issue #67）——协作体系 v1 的七宗罪，摘三条：
  • 复核缺位：qa 角色没有接入状态机，大 PR 没有代码级复核闸 → 补（#58）
  • 状态不可见：agent 做到哪一步要靠翻会话 → 引入格式化状态行 + 流转标签
  • 权限太粗：只有「能做/不能做」，缺「有条件能做」 → 引入 pending-ratification（先做后追认）与紧急通道
  • 方法论：协作体系本身也走「发布 → 观察诉求 → 复盘 → 迭代」，跟产品一样
这页的核心信息：没有第一版就对的协作体系，只有迭代出来的。我们如今看到的所有顺滑流程，背后都有一轮复盘出七条罪状的狼狈。
05 失败与迭代

失败案例二：AI 的三类典型事故

类型案例制度回应
静默断链依赖靠 root hoisting 隐式可用，包内未声明（#437）——删一个无关 devDep 全仓炸契约校验 + 显式声明门禁
口径漂移同一件事在文档/CI/脚本里三处口径不一致（#438）单一事实源纪律（gauntlet.config.json）
表象服从AI 声称 UI 改好了，但从未打开浏览器看过（#51 起源）证据文化：隔离实测 + 截图归档 + CI 证据门禁（#121）
  • 共同点：都不是代码写错，而是「声明与现实脱节」——AI 对世界的认知全部来自你给它的文本，文本错了它就错得很自信
  • 所以治理重心从「审代码」上移到「审声明」：依赖声明、口径声明、完成声明
「审声明」是本页要留下的新词。三类事故可以各配一句吐槽，但落点必须回到制度回应——观众要带走的是右列。
05 失败与迭代

失败案例三：给 agent 的判据要像合同，不要像愿景

  • 「通知完成误报」bug 修了三次（#7→#49→#290）：每次判据都「对」，每次都漏一种世界
  • 教训：给 qa/judge 的验收判据必须是可枚举、可证伪的条款——「fork 型委派且 parentSession 归属时不得发完成通知」，而不是「正确识别子代理」
  • 模糊判据在人类团队里靠默契兜底；agent 团队没有默契，模糊判据 = 没有判据

一个实操习惯

规格里的每条验收判据都问自己：「一个只想过关的 agent 能不能钻这个空子？」

能，就再具体一层。判据是防「聪明但没立场的执行者」的合同条款，不是给人看的表扬信。

这页与 v1 的「三次变形」故事共用素材但角度不同：v1 讲质量，v2 讲判据设计。提醒听众：如果你只带回一页，带这页——判据质量决定 agent 产出上限。
06 演进

三代工作流：从手工作坊到 loop engine

代际形态瓶颈
v1 手工人在会话里逐个指挥 agent 干活人是瓶颈：切上下文、丢状态、忘跟进
v2 脚本化固定流程写成编排脚本，批量执行刚性：异常全靠人兜底，复核缺失
v3 loop engineissue 状态机 + 计划门 + 计圈收敛 + 标签授权，agent 自治循环、人守闸门当前形态：人的时间集中到方案与红线
  • 演进不是重写，是每次只解决上一代最痛的一个点：先省人力、再保质量、最后定权限
  • 附产品：方法论沉淀为 skill（oss-pipeline / triage / steering / report），人换项目体系跟着走
三代演进的时间跨度只有几天到一周——AI 组织的好处是体系本身也能高速迭代。但提醒：跳代不划算，v1 的手工期是理解所有异常场景的学费。

07 反思

反思：什么时候不该让 AI 自治

  • 方向类决策：做什么插件、砍什么功能——agent 只能优化给定目标，不能选择目标
  • 有长期承诺的接口：公共 API、发布版本、依赖选型——错一次的代价由未来的自己付
  • 需要品味的地方：UI 打磨、文案语气、架构美学——agent 能达到「不丑」，到不了「讲究」
  • 事故善后：紧急发版可以 AI 执行，「要不要发」必须人拍板（24h 追认机制就是这么来的）

反向自查

每次 AI 产出不满意时问一句：这是执行问题还是我给的题就不对？实测中，后者居多——而它不该怪 AI，该改规格或改决策。

这页防分享变成「AI 万能论」。真实经验：把方向类决策错误地丢给 agent，得到的是高效地跑错方向——比慢更糟。
07 反思

人的角色迁移：从生产者到「体系架构师」

  • 过去：写代码 → review 代码 → 修 bug → 发版（时间花在产出上）
  • 现在：定判据 → 审方案 → 批红线 → 复盘体系（时间花在「让产出可信」上）
  • 核心技能变化：把模糊意图写成可执行判据的能力，成为新的第一生产力
  • 直白说：AI 时代最贵的不是会写代码的人，是「知道什么是对的」的人

对管理者的启示

评估一个人时，看他写的代码不如看他写的判据：判据的质量决定一个 agent 化团队产出的上限。

对个人贡献者：你最好的晋升材料，可能是你写的那份「验收判据」而不是你写的类。

这页是全场人文落点，放慢语速。「知道什么是对的」不是虚话——前文所有案例（口径、判据、红线）都是它的注脚。
08 落地

在公司团队落地的最小集（不是照搬全部）

  • 第 1 周：留痕——所有 agent 产出必须挂 issue/PR，禁止只活在会话里（会话会死，issue 永存）
  • 第 2 周：分级——列出你们团队的「红线清单」（API/依赖/CI/发布），红线外自治、红线内人批
  • 第 3 周：复核——重要改动引入一次独立上下文的对抗评审，成本几乎为零
  • 第 4 周：判据——验收标准从「看着行」改写为可证伪条款， qa 与实现角色分离
  • 持续：每轮复盘体系本身——流程也是代码，也要迭代

先从哪类任务试点

测试加固 / 依赖升级 / 文档同步 / 明确规格的 bug 修复——特征：判据清晰、风险可回滚、验证可自动化。别一上来就让 agent 碰核心架构。

给公司听众的干货页。强调「最小集」：今天展示的完整体系是 20 天长出来的，落地别贪全，按周推进。
Q&A

管理 AI 团队与管理人类团队，
唯一不变的是：体系决定产出上限。

区别只是：AI 团队的流程不需要哄、权限必须防穿透、判据必须可证伪——
而这三件事，对人类团队其实也成立，只是从没有人逼我们做到这么严格。
