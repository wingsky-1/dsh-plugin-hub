背景

复盘对象：dsh-plugin-hub 是什么

  • DSH（DeepSeek Harness）Web GUI 的插件集，npm 分发：一键装全家桶，或按需单装
  • 8 个插件：通知中心 / MCP 管理器 / 局域网代理 / 用量统计 / 文件预览 / 代码图谱 / 隔离验证 …
  • 形态：monorepo（pnpm workspace）+ CI 门禁 + tag 触发自动发版
  • 关键约束：绝不修改宿主源码，只走官方扩展点挂载——宿主是上游，我们是生态位
  • 它不是玩具：64 个测试文件、21 段变异测试配置、五条 CI 工作流
一句话定位即可，不要陷入功能演示。强调「这是真实在 npm 上发布、每天在用的东西」，为后面的质量话题铺垫可信度。

01 时间线

阶段 2 的账单：速度的利息

  • notifier 一个包 35 个提交，21 个是 fix——fix 比功能还多
  • SSE 连接泄漏：0.1.8 发出去当天出事，紧急发 0.1.9 并在 README 挂「请弃用 0.1.8」（issue #2）
  • 「2 台设备，显示在线 24 个连接」——连接表只增不减（issue #330）
  • 子代理完成被误报为任务完成（issue #7）——同源 bug 后来又变了两次姿态

当时的心态

AI 出活太快，一个晚上一个插件就能从 0 到能用。每一次「先发出去再说」，都是在给未来的自己放高利贷。

代价清单

紧急发版、用户侧升级成本、深夜排查、以及最贵的——对「这个仓里还有多少颗雷」失去把握。

这页是「为什么要踩刹车」的情绪铺垫。SSE 泄漏是最好的例子：功能完全正常，但资源生命周期是错的——AI 写代码时最容易欠的就是这类账。
02 转折点

三个事故，把方向从「更快」掰到「更稳」

事故表象根因类型
SSE 连接泄漏 #2/#330通知重复、连接数虚高、浏览器发热资源生命周期——功能对，清理错
MCP 自激循环 #324切换目录后每 500ms 一次高频自激 GET反馈环失控——轮询去刷新「轮询状态」
子代理误报 #7→#49→#290任务没做完，通知先喊「完成」边界条件——判据只覆盖了想象中的路径
  • 共同点：三个都不是「AI 写错了语法」，而是「人类 Review 也很难看出来的系统性缺陷」
  • 结论：Review 环节必须升级——不能再靠眼睛，要靠机器化的验证与度量
讲自激循环时可以展开 30 秒：为了刷新 MCP 状态发了一个请求，这个请求又触发了刷新——AI 对「系统里还有谁在动」没有全局图。这就是后面所有工程化投入的动因。
03 三件武器

第一性原理：瓶颈已经转移

AI 把「写代码」的成本打下来之后，
整个工程的第一瓶颈变成了 验证。

  • 以前：写慢、验证快（人写代码一周，跑个测试几分钟）
  • 现在：写快、验证慢——产出速率被验证速率卡死
  • 推论：投资回报最高的地方不再是「写得更爽」，而是「验证得更狠」
  • 佐证：20 天里「meta 类」issue（质量/流程/基建）占了 25 个 scope 分组之首

验证金字塔（本项目实测版）

① 静态门禁：构建契约 / 类型 / 打包校验
② 行为门禁：smoke + 单测 + 覆盖率/CRAP
③ 元验证：变异测试——验证「验证本身」有效
④ 证据：隔离环境实测 + 截图归档

这是全场的论点句，后面三件武器分别对应金字塔的四层。可以在白板上画一下：传统「开发→测试」漏斗，现在是「生成→验证」漏斗，漏斗的宽窄颠倒了。
03 三件武器 · 武器一

武器一：把「合格」变成一台机器

  • 合并前置门禁，一条命令跑完：pnpm build && pnpm test && pnpm contract && pnpm pack:check && pnpm typecheck
  • contract：构建产物契约校验——客户端模块形态、路由围栏、patch id 规范，机器说了算
  • pack:check：发布物边界校验——内联了哪些第三方库、license 归集是否完整
  • CI 按路径过滤只跑受影响子包（#85）；Windows 加独立构建 runner（#121）
  • docs-only 的 PR 不触发全量门禁——门禁也要省着用，别把人逼成「绕门禁专家」（#432）

关键认知

门禁不是给「坏人」设卡，是给「人和 AI 都会疲劳」这个事实兜底。门禁的反馈速度决定它会被爱还是被绕：全量跑 20 分钟的门禁，一定会催生投机。

强调两点：契约门禁把「规范」从文档变成代码（AI 最听机器的话）；门禁设计本身有工程量（路径过滤、docs-only 跳过都是踩坑后加的）。
03 三件武器 · 武器二

武器二：覆盖率不够，还要 CRAP

  • CRAP = 复杂度 × 覆盖率：一段又绕又没测的代码才是真正的雷
  • 100% 覆盖率可以靠「只测快乐路径」刷出来；CRAP 刷不了——复杂分支必须逐条喂测试
  • 阈值唯一事实源：scripts/data/gauntlet.config.json，CI 卡点
  • 首期清零 55 个超阈热点并收紧阈值（#82）

口径修正：覆盖率也会撒谎（#79）

构建期 esbuild 把第三方库内联进产物，c8 连 vendor 一起统计——覆盖率虚高一大截。修正：排除 vendor，单独报告 self-written 覆盖率，夜间硬校验。

度量指标的第一性问题：你必须知道你在度量什么。

CRAP 这个名字自带喜剧效果，可以用它拉回注意力。核心观点：AI 时代「生成复杂代码」零成本，所以「复杂且没测」的堆积速度是以前的十倍——这个指标恰好专杀这种堆积。
03 三件武器 · 武器三

武器三：变异测试——测「测试的有效性」

  • 原理：把代码故意改坏（条件取反、返回值替换…），如果测试还全绿，说明测试是摆设
  • 工具：Stryker，只对 self-written 函数开 mutation（#80/#92）
  • 它抓住的是「覆盖率 OK 但断言无效」：测试跑了、没真的验证
  • 传统覆盖率的盲区：行执行了 ≠ 行为被断言了

为什么 AI 时代特别需要

AI 写测试很快——写「假测试」也很快：断言宽松、mock 一切、永不失败。变异测试是唯一把「测试质量」本身变成可度量指标的常规武器。

本项目形态

21 个分段配置（lan-proxy 4 段 / mcp-manager 6 段 / notifier 4 段 / provider-usage 6 段 / wfp 1 段）+ 增量基线缓存（#178）

先讲原理再讲为什么（30 秒内讲清「杀变异体」这个概念），细节留到故事章节。听众若有 QA 同事，这里是他们最有共鸣的一页。
03 三件武器 · 武器三

驯化一头怪兽：变异测试的提速战

  • 全量变异测试太慢，直接威胁「门禁反馈速度」——于是打了一场持续一周的提速战：
  • #179 耗时优化立项（目标：单段 < 2 分钟）→ #220 按模块拆段 + concurrency 超订 → #342 单段仍超 2 分钟，二次拆段
  • #187 事故：一个 re-export 让 lib 行号偏移，21 段配置的 mutate 区间全体漂移，夜间守卫直接判红 → 区间改为从源码自动派生（#276）
  • #204：增量基线按 ref 隔离没做好，PR 永远 cache miss、静默降级全量——基建的 bug 最擅长「安静地变慢」
  • 最终形态：PR 跑增量分段，夜间全量 + 四班次增量观察（#433），全量构建放北京时间 4 点
这页的落点：引入重型质量工具不是加个配置，是一套「工具自身的工程」。如果听众只记住一句：让慢工具变可用的办法是「分层 + 增量 + 自动化派生」，不是「少跑」。
04 制度化

证据文化：口说无凭，截图为证

  • 约定（#51）：插件界面改动，必须隔离环境实测 + 截图归档到 docs/archive/，issue/PR 双向引用
  • CI 截图证据门禁：客户端改动的 PR 缺证据就不算完成（#121）
  • 隔离纪律：临时 DSH_HOME + 独立 profile + 独立端口——验证不许污染正在使用的环境

为什么 AI 协作特别需要

AI 说「我改好了、看起来没问题」——它没看过浏览器。它的「没问题」是脑补。

证据约定的本质：把「我相信」变成「我看到」，而看到的那个人必须是独立的复核角色，不是写代码的角色自己。

举一个真实例子：dsh-verify-isolated 插件就是这套约定催生的工具——验证动作本身被自动化成一键脚本。好约定会自己长出工具。
04 制度化

防 flake：测试的可信度比测试的数量重要

  • #313/#315 系统性整改：固定 sleep 等响应 → 改轮询等待条件成立——「等 500ms」和「等到它发生」是两种世界观
  • #181 时间边界 flake：quietHours 配 00:00-23:59，在 23:59 那一分钟跑测试就不覆盖——时间相关测试必须注入时钟
  • #217 端口竞争：变异测试矩阵并行跑全仓 smoke，端口打架——测试隔离要连端口一起隔离
  • #218 测试产物零污染：运行时落盘必须进 mkdtemp 目录，出现 packages/*/undefined/ 就是事故

一条红线的价值

flake 测试的危害不是「偶尔红」，是「红着红着大家就学会无视红色」——整个门禁体系从此失效。所以防 flake 不是测试优化，是门禁体系的生存问题。

可以问听众一个问题：你们 CI 上有没有一个「大家都知道忽略它」的红色按钮？有，说明防 flake 已经欠债了。
04 制度化

AI 协作流水线里的质量设计（预告 v2）

STEP 1方案门公共 API / 依赖 / CI / 发版类改动，必须在原 issue 出方案、打 needs-proposal-review，人工批准才许动手
STEP 2隔离执行独立 worktree 写码，主 checkout 永远干净；构建测试全在隔离环境
STEP 3独立复核qa 角色按验收判据判收，重大 PR 再拉一个无先入之见的子 agent 做对抗评审
STEP 4证据归档截图 / 测试输出随 PR 入库，评审遗留项分三桶跟踪，不许「下次再说」
  • 权限分离：zone/auto 可自治、zone/red-line 必须人批、approved 标签永不许 AI 代打
  • 写代码的 agent 和判断「写得好不好」的 agent 必须分角色——裁判不能是运动员（细节在 v2 展开）
这页 90 秒带过，重点是「质量不是工具，是流程角色设计」。留钩子：如果对这套 loop engine 感兴趣，那是另一场分享。
05 故事

故事一：同一个 bug 的三次变形

回合表象修了什么
#7子代理完成被误报为「任务完成」判定加了 delegationDepth
#49fork 型委派仍误报——新路径绕过判据origin 判据补 parentSession + 运行时归属
#2900.1.13 通知静默丢失——ctx.agents 未注入时直接抛错防御注入缺失 + 事件作用域过滤
  • 每次都「修好了」，每次都有下一个变体——修 bug 修的是表象，测试钉住的才是类
  • 最终靠变异测试把这一类判据钉死：任何改写 isSubagentOf 语义的变异，测试必须能杀死
  • 启示：对 AI 生成的边界判断代码，问「这个判据漏了哪种世界」比问「这样写对吗」有效
讲成侦探故事，节奏放慢。三次变形分别对应：深度判定、来源判定、环境判定——bug 在考验你对整个调用图的理解。
05 故事

故事二：质量基建自己也会回归

  • #187：一个无害的 re-export，让构建产物行号整体偏移 → 21 个变异分段区间全体漂移 → 夜间守卫判红
  • 处置：mutate 区间不再手写，改从源码结构自动派生（#276），并建立「区间漂移」的 fail-loud 告警（#235）
  • #423：发现 30 个测试副本靠手工双向同步——本身就是 flake 温床 → 改为自动生成/复用
  • #437：依赖靠 root hoisting 隐式可用、包内未声明——删一个 root devDep 就断链，而且断得莫名其妙

元认知

你引入的每一个质量工具，自己也是需要被治理的代码：配置会漂移、基线会过期、脚本会腐化。

工程化的完整体 = 工具 + 工具的防回归 + 工具的可维护性。

这页适合工程师听众深聊：tsconfig/CI 配置/测试基建是「代码的代码」，它们的回归往往以「静默变慢 / 静默漏检」的形式出现，比功能 bug 更隐蔽。
05 故事

故事三：你没测的端，就是会炸

  • #98 Windows：execFileSync 调 esbuild 没带 shell，.cmd 解析失败直接 EINVAL——Linux 上永不复现
  • #238 Windows：toast 脚本缺 UTF-8 BOM（PowerShell 5.1 解析失败）+ -Name=Value 参数绑定不生效——所有 Windows 通知全坏，而 CI 全绿
  • #268/#308/#412 手机端：切后台再切回，半开连接挂起、接口卡死、MCP 掉线——桌面开发时永远遇不到

制度回应

CI 加 Windows 构建 runner（#121）；多端兼容写进开发规范：三操作系统 × 三访问形态（桌面/平板/手机）× 明暗双主题，客户端 UI 改动按矩阵自测并归档证据。

AI 协作的放大效应

AI 只了解你给它看的运行环境。你不测的矩阵象限，AI 一样不测——盲区不是被 AI 消灭了，是被 AI 高速复制了。

toast.ps1 那个案例值得展开 1 分钟：BOM 是给 PowerShell 5.1 认编码用的，参数绑定是 PS 5.1 不支持 -Name=Value 语法——两个坑叠在一起，且只在 Windows 出现。CI 绿 ≠ 可用。

这页回答老板视角的问题：花在质量上的 40% 时间值不值？回答：看紧急发版次数——转折之后再没有过。事故成本永远比预防成本贵。
06 收束

反思：过度工程化的护栏

  • 不是所有指标都要立刻卡死——观察期机制：crap 指标先只记录不判红，等基线校准后再纳入完成定义
  • 观察期开关曾分散在 6 处靠注释互指（#440）——连「临时方案」都需要单一事实源
  • 门禁不是越多越好：docs-only PR 曾被全量门禁误伤（#432）——门禁对「无风险变更」也要让路
  • 维护型提交（observe 报告 / 周报）由夜间流水线自动开 PR，不占人工注意力（#433）

一句话

质量工程的成熟标志不是「门禁多严」，而是「每一道闸门都知道自己为什么存在、什么时候让路」。

06 收束

AI 时代的质量公式

生成成本 → 0 之后，
竞争力 = 验证吞吐量 × 学习速度。

①把规范变成机器可执行的契约——AI 听机器的话，不听文档的话
②度量必须诚实——口径错了（如 vendor 混入覆盖率），决策全错
③验证「验证」本身——变异测试专杀假测试
④证据先于结论——截图与实测是 AI 协作世界的硬通货
⑤盲区会被高速复制——测试矩阵要覆盖你没亲历的端

06 收束

给团队的五条可复制建议

  • 第一周先立契约再上量：构建/测试/打包三道门禁跑通之前，别让 AI 产能放开跑——否则利息吓人
  • 覆盖率看口径，CRAP 看热点：先清热点再谈阈值；vendor 与自写代码分开统计
  • 给重型工具分层：PR 跑增量、夜间跑全量；任何门禁超过 10 分钟必须有增量形态
  • 证据制度化：UI/行为改动必须有独立环境实测证据，复核角色 ≠ 实现角色
  • 把 flake 当 P0：出现「可忽略的红」当天修，修不掉就先摘除——门禁的可信度是整座大厦的地基
这页是对公司场景的落地翻译。可以预告：这五条的每一份实施细节（配置、脚本、流程）都在公开仓库里，会后发链接。
