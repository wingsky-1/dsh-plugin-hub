# Agent Note: 跨包骨架用 core 包承载被否

Status: rejected — 新增包是仓库级变更，发布物自包含加构建期内联下又无运行时收益，实测重复度不足以支撑新增一层，故跨包骨架统一放 `shared/`

## Problem

跨包复用原先只有仓库根 `shared/` 一条路，形态是构建期源码依赖：各包以跨目录相对路径
import，构建期内联进自家产物。它承载轻量工具函数与类型没问题，但当要放跨包架构骨架
时有两处不适配：一是相对路径引用随包内搬迁碎裂，二是共享代码拿不到独立的
tsconfig、独立测试与独立版本策略。有人据此提议新增一个 core npm 包专收跨包骨架
（当时的提案文件 docs/proposals/core-package.md，状态「提案，未批准」，已随本次否决
删除），并把准入规则定得比 `shared/` 更严：≥3 消费者、须已被 2 个以上包以近似重复
形态各自实现。

## Proposal

新增 core 包承载跨包架构骨架，各包删掉包内与 `shared/` 中的对应副本、改经包名引用它的
导出面；新包与各包同等受构建链内联，发布物仍自包含，不作为运行时 npm 依赖分发。
轻量工具型模块留在 `shared/` 原地，两层在可预见期内并存。

## Alternatives considered

### 共享层（shared/）承载跨包骨架（被采纳）

对方最强的理由：core 包想要的收益，扩容 `shared/` 大体都能拿到。消费方由
`scripts/gate/verify-shared-fanin.mjs` 按生产 src 口径实时派生（不靠人肉快照，
shared/README.md 明确不登记消费方），类型双写有既有门禁兜底，独立测试与独立变更记录
在 `shared/` 内也能按模块写。留下的代价只是继续承担 `.js` + `.d.ts` 双写与相对路径
引用随包内搬迁碎裂（后者靠评审保证，无工具强制）。

采纳理由三条：

- 新增包是仓库级变更：触发聚合包校验与 npm 布局校验，包命名、聚合 patch 生成、
  版本一致性策略要同步，构建链要新增「从 workspace 包内联」的支持，第三方许可归集
  链路要覆盖新包内容。
- 发布物自包含加构建期内联的模型下无运行时收益：内联即分发副本，跨包引用与
  `shared/` 的相对路径引用一样在构建期内联成每包一份，不产生共享实例。core 包相对
  `shared/` 多出来的是工程化待遇，不是运行时能力。
- 实测重复度不足以支撑新增包层级。重复确实存在（逐字相同、无包级语义分叉的骨架层
  以升级链为代表），但重复的规模与位置配 `shared/` 已有的准入与登记约束即可消化，
  撑不起「新增一层」的仓库级代价。**注意下沉过的只有 `shared/upgrade-tick.js`
  这类零逻辑部件（空步）；带编排的骨架层此前一律自持**，本篇否决的正是「为它们
  再开一层」。

骨架型内容下沉 `shared/` 走零分叉判据：算法与实现逐字相同、无包级语义分叉（无包级
常量、无包级命名、错误模型与队列位置不分叉）才下沉；有分叉的部分留在包内，需要复用时
经 port（`deps.ts` 注入面）参数化，不把分叉搬进共享层。

### 维持各包自持（被否）

对方最强的理由：零成本、零新层级，与本仓已落地的两条否决记录同构——落盘 IO 三向
分叉、placement-math 包级常量与公开命名分叉，都证明包级事实分叉时下沉只会把分支藏进
共享层。各包自持、同形靠评审保证，代价可控。

否决：本次不选。实测确有逐字重复的骨架层，算法与实现逐字相同、无包级语义分叉，
正是零分叉判据的达标形态，把这份重复留在包内就是明知可下沉而不下沉。

注意本次否掉的只是「一律自持」这条总路线，不是「一律下沉」：包级事实分叉的内容
（落盘 IO、placement-math）仍按各包自持处理，与本篇不冲突。

## Consequences

- 收益：跨包骨架与轻量工具统一在 `shared/` 一处选型，本仓不再有「要不要为共享再开一
  层」的常设争议面；逐字重复的跨包骨架可直接下沉并登记消费方与行为契约，不必为它
  单独改构建链、单独走仓库级红线评审。
- 代价：`.js` + `.d.ts` 双写的类型漂移面继续由门禁兜底而非结构性消除；相对路径引用
  碎裂靠登记与评审约束，不靠工具强制。若日后 `shared/` 的重复度与双写维护负担显著
  上升，重开议题的入口是「实测重复度」，不是「core 包」这个名字。
