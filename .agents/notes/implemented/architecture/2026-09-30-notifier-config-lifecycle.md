# Agent Note: dsh-notifier 配置生命周期：读面两通道 + 写面五态按字段合并

Status: implemented

## Problem

一份 dsh-notifier 配置在系统里被反复翻译：磁盘原样 → 读面归一化（补默认值 / 剥空串 / 钳越界 / 丢弃半坏条目）
→ 掩码 → 客户端比较 → 掩码还原 → 校验 → 落盘。每一层各持一份「什么值合法」的知识，两边可以给出相反答案，
而**没有任何一层负责保证翻译可逆**。由此长出三条既有缺陷（都不是本 PR 引入，`origin/main` 上即可复现）：

- A（P1）：磁盘上 webhook 缺 `token` / `password` / `headerValue` 任一，用户下次改**任何**字段都 400
  「新增频道不能提交掩码占位」——读面把缺席补成空串，空串被掩成占位，客户端剥不掉空串，写面按 id 取回原值时
  拿到 undefined，遂拒掉整批。真实路径是设置页新建 webhook 后**只切一下 enabled 开关**。
- B（P1）：磁盘频道上有陌生键 → 读面收进 `extras` 子对象 → 客户端原样带回 → 写面只放行 string/number，
  遇到这个对象直接 400 —— 该频道所在配置从此再也保存不了，与 README 承诺的「陌生键原样保留」正面冲突。
- C（P2）：磁盘两条同 id、凭据不同的 webhook，保存一次之后第二条的凭据被静默改成第一条的。

根因落在两个具体动作上：`channels` 过去是**整组替换**（提交的那份整个盖上去），于是**客户端没在 patch 里
带的字段，落盘后就没了**；读面把补出来的默认值**外发**给了客户端，于是「宿主的解释」被当成用户存过的值
写回磁盘。而「一份配置能不能被解释」这件事，仓里没有任何一个地方说了算。

## Decision

**形态变换只发生在 upgrade 域**；读面有两条出口，写面按字段合并，判据收敛为一份事实源。

### 读面拆「投递投影 / 视图投影」两条通道，投影绝不外发

`ConfigStore.adopt()`（`config/impl/service/index.ts:191`）是唯一落点：
同一份磁盘内容派生两份投影，二者此后互不相干。

- **投递投影** =`normalizeConfig(stored)`：缺键补默认、越界钳回合法域、认不出的条目丢弃。它喂
  `current()`（`service/index.ts:94`），域内消费者（pipeline / sdk / stores / dry-run）一行未改。
- **视图投影** =`projectForView(stored)`（`config/impl/service/view.ts:46`）：纪律是
  **除掩码外一个字都不改**——不补默认值、不钳越界、不丢非法值、不补内置条目、不投影旧键。

不变式是「宿主的解释不得外发」：补出来的默认值一旦交给客户端，客户端会把它当用户存过的值原样提交回磁盘，
一次无关保存就把磁盘形态改写成读面的实现（越界值被钳成 0、非法枚举被换成 custom），而用户什么都没碰过。

视图有两处刻意的例外（`view.ts:15-21`）：顶层只取 `DEFAULT_CONFIG` 的 11 个键——写面对未知顶层键一律 400，
交给客户端只会被原样带回并当场被拒；顶层缺键取默认表的值——设置页要渲染全部 11 个控件。
另有一条承重依赖：**视图不做任何键名映射**（`view.ts:40`），磁盘上的陌生键正是靠「客户端原样带回 +
合并判它原样带回」才既不丢也不撞 400。

### 写面五态按字段合并，掩码并入合并态

`config/impl/service/merge.ts` 把一个频道条目拆回逐字段的决策，五态（`merge.ts:8-15`）：键**缺席**不动；
值为掩码字面量按该键是不是密钥字段分三段；值为 `null` 删键；值为 `""` 且非必填删键；其它值写入。
外加四条硬规则，都判在删键之前：必填键传 `null`/`""` 400；掩码无原值可还原 400；掩码落在**别的 type**
的密钥字段名上 400；删键之后由调用方重新校验合并结果。

顺序不可换（`service/index.ts:144`）：**合并先于校验**，判据审的是合并结果
（`validateSettingsWithMerge`，`config/impl/input/index.ts:232`）。合并的基底取 `stored`（磁盘原样）
而不是 `effective`——拿归一化补过值的结果当基底，等于把一份补值写回文件。

合并同时交出**两笔账**：`inherited` 记「值原样来自存量」的字段（值域判据只审不在其中的），
`preexisting` 记「必填键的缺席本就来自存量」（`merge.ts:87` 与 `merge.ts:101`）。两笔账问的是两个不同事实，
合成一条会让两种判据都说不清自己为什么跳过。

**掩码不再由 redact 域单独解一次**，它是五态之一。留着两条路径各解一次，「掩码在哪一步变成原值」就有两个答案，
而判据看到的形态与落盘的形态必须逐字一致。两句拒绝话术的事实源放在写面
（`merge.ts:56` 的 `NEW_CHANNEL_MASK_HINT`、`merge.ts:71` 的 `RESIDUAL_MASK_HINT`），dry-run 从这里 import
（`config/impl/draft/index.ts:20`）——同一份草稿在保存与试发两条路上不许给出两个答案。
`unmaskChannels` 仍在 redact 域，但生产写面 diff 0 行，消费者只剩 dry-run。
掩码只掩**非空串**（`redact/index.ts:88`）：空串在这份配置里表示「未设置」，掩了它还原侧会拒掉整批。

客户端相应地把「清空」表达成 `null` 而不是删键（`client/settings/diff.ts:155`），`RawSettingValue`
因此加进 `null` 一支（`config/impl/model/type.ts:23`）——键缺席与键为 null 从此是两种手势。

### 0.2.8 形态清理接住「读面不再兜底」的后果

读面不再物化，兜底搬进 upgrade 域新增的 `canonical-keys.ts`（挂载点
`upgrade/impl/steps/index.ts:38`）。判据一律「条件 → 删/补」，**不猜值、不夹值**：越界值删键而不是
改成边界值，静默改写用户输入比留下一个非法值更糟；干净形态下返回 null，**一个字都不写**（否则每次启动都重写
文件，把用户手改的格式重新序列化）。只清理「本版本不可能是合法形态」的值，不清理「合法但非默认」的值。
这一步是本插件**唯一一步会丢弃取值**的升级步，迁移条目逐类写明（`packages/dsh-notifier/README.md:485`）。

两条方向相反的处置，边界在**「键在不在」**（`canonical-keys.ts:373`）：

- 必填键**空串或缺席** → 整条保留。这是用户手改出来的残缺，S3 已给它修通三条路：视图逐字外发、写面按
  `preexisting` 放行、投递投影本就整条丢弃（`config/impl/input/index.ts:789`）。删掉它剩下的只有代价：
  连 `name` 带其它字段一起静默消失。
- 必填键**值形态不符**（`baseUrl: 12345`）→ 删整条。这是本步**自己造出来的**残缺，删键等于当场制造一条它刚
  承诺要整条保留的半坏条目。

### 判据收敛为单一事实源

`packages/dsh-notifier/src/shared/config-schema.ts` 是零 import 叶子，客户端渲染与宿主校验读同一份。
清理步此前自维护一份必填键集合与 `historyMaxAgeDays` 上界并注明「刻意不落在 shared」，而那份「刻意」正是
它能造出残缺条目的根：清理步过去压根没有「哪些键是必填」的概念，于是值形态判据对必填键与普通键一视同仁地删键
（`canonical-keys.ts:33`、`config-schema.ts:89` 记着这次反转的理由）。现在必填键清单、已知键、取值域与计数上界
全部读 `REQUIRED_KEYS`（`config-schema.ts:83`）、`BARK_KNOWN_KEYS`、`HISTORY_MAX_AGE_DAYS_LIMIT`、
`BARK_TIMEOUT_MS_LIMIT`、`WEBHOOK_TIMEOUT`。读面读同一份不落第二份的还有 `isDeliveredRequired`
（`input/index.ts:658`）——「空串算不算在场」只有这一句。

## Alternatives considered

### 整组替换（被否）

对方最强的理由：它是唯一能同时表达「新增频道」「删掉一条频道」「整条重写」的模型，实现最短，掩码还原的
`findById` 与它天然同构（都按 id 找一条存量），不需要引入任何记账。

否决：它与「键缺席 = 不动」正面冲突，也正是缺陷 B 的根因——提交面就是全部，客户端没带的字段落盘后就没了。
按下标对齐的老问题（数组一换序就把 A 的凭据回填进 B）它也没解。改成按字段合并后，**换型仍按整组处理**
（`merge.ts:281`：字段集随 type 变，存量那批键对新类型是陌生键），所以「换型之后提交面就是全部」
这条老行为被完整保留，不是一次无差别的行为变更。

### 写面保留 scope/基面机制（被否）

对方最强的理由：它实测假阳性为零（canon-base 列全 0，另两种基线取法是 3~8 个字段的假阳性面），且是下游边界判据
（重复 id / URL 写面 / 边界值）唯一要接的缝。完整否决记录见
[写面保留 scope/基面被否](../../rejected/architecture/2026-09-30-notifier-channel-write-scope.md)。

否决：它诞生在**整组替换**的世界里，那时「提交面就是全部，缺一个键就是用户删了它」是对的；改成按字段合并之后
同个手势有了相反的答案。两套并存时落盘只有一个结果，判据却会拿到两个裁决。

### 0.2.8 判据 #6「缺必填键 → 删整条」（被否，选 (a) 不删）

对方最强的理由：一条打不通的频道留着会让此后每一次无关保存都被拒（这正是 S3 复核 P1-2 的原始判断），
且删掉只发生在刻度推进那一刻，用户当下看得到的是「升级后我那条频道不见了」。

否决：三条路在 S3 之后已经齐了——视图逐字外发（看得见、改得动、也删得掉）、写面按 `preexisting` 放行
（`merge.ts:91`）、投递投影本就整条丢弃。于是「删掉它」只剩代价，没有收益。
反向也成立：一旦把删除这条判据拆掉，读面那一句就成为**投递侧唯一的一道**，两侧必须一起读。

### 「删 `preexisting` 收窄概念」（被否）

对方最强的理由：半坏条目在本 PR 之后**没有任何正常用户路径能造出来**（UI 点新建不填地址直接被 400 拒、
API 直调与未知 type 全被拒、升级割接保留不删也从不造、投递投影本就丢弃），唯一可行路径是手改 `config.json`；
而 `inherited` 必须保（它防的是每天都在发生的「用户没碰过的键」）——那 `preexisting` 防的就是自己造不出来的状态。

否决（红队逐条核过后证伪）：前提「造不出来」不成立。**清理步自己会造残缺**：判据 #5「值形态不符 → 删键」
作用在必填键上时，会把这个键删掉、当场造出一条半坏条目（现已改成必填键形态不符即删整条，但边界仍在同一段代码里）；
**降级安装不可自愈**：用户从 0.2.8 装回 0.2.7（link 安装很常见），新版本写的字段旧版本不认，再升级回来时
那次中间态留在磁盘上，而清理步只在刻度推进时跑一次。删掉 `preexisting` 的症状不是「400 锁死」，
而是「半坏条目从此永远存不下去」——比现在更差。本轮只消除病根（判据单一化），**不收概念**。

### 掩码留在 redact 域、写面调一次还原再调一次合并（被否）

对方最强的理由：还原与合并是两种关注点，合成一处会让 `merge.ts` 同时管「掩码协议」和「合并策略」。

否决：合成处仍然是「逐字段决策」这一件事——掩码在某个键上的含义就是「用户没改它」，与缺席/null/空串同属
五态。两处各解一次时，「用户交上来的形态」「判据审的形态」「落盘的形态」三者有两份答案。

## Consequences

- 收益：读面两条通道各自单一职责，投递侧零回归（`current()` 一行未改）；写面提交面与落盘面之间只剩
  「本次提交做了五态中的哪一种」这一个待决问题；升级域独占形态演进，读面不再认历史形态
  （旧顶层键回落分支全删）。
- 代价：客户端与写面之间多了一条必须同时读的依赖——视图不做键名映射。改动客户端
  `stripChannelEmpties` / `normalizeChannelForCompare` 的键清单时必须一并重看 `view.ts` 那段。
- 边界：`channels` 按字段合并，**顶层键维持整值替换**（顶层没有按键合并这回事）；换型按整组处理；
  内置条目的字段集固定五六个，不按 `inherited` 跳过。
- 承重不变式：0.2.8「必填键空串或缺席不删整条」与读面 `outboundChannels`（`input/index.ts:789`）
  必须一起读。任一侧单独删掉，半坏条目会从「被整条丢弃」变成「留在投递池里每条通知白记一次失败」。
- 文档镜像：本篇的对外口径见 notifier README 的 0.2.8 迁移条目与掩码规则（代码为事实源、README 只镜像，
  见[配置与契约文档以代码为单一事实源](../process/2026-09-18-config-doc-mirror-policy.md)）。

## Testing

- 10 种磁盘形态的回归断言从「假阳性 = 0」升级成**落盘形态回归**：每种形态断言「走完真实往返链、只改 name
  之后，落盘的那条频道逐字等于**手写**的预期形态」（`test/integration/config-merge-roundtrip.test.ts:14`）。
  合并、读面归一化、出口掩码、客户端剥空串任一处漂了都会打红其中一条。
- 升级步的判别力集中在 `test/unit/upgrade/steps.test.ts`：判据 #5 第二格（必填键值形态不符 → 删整条，
  `:250`）、判据 #6 的**反转**（半坏条目整条保留、逐字不动，`:333`）、幂等与「干净形态连缩进都不变」（`:510`）。
- 测试面随实现改名连带三处台账（`scripts/data/mutation-topology.json` 的 config/channels/client 三段、
  `scripts/test/service-contract-wiring.test.ts:232`）与四份派生的 stryker 配置（`vitest.stryker.d/*.config.ts`），
  改完跑 `pnpm stryker:gen` 重派生；一个测试文件随 scope 面删除（`service-write-scope-baseline.test.ts`）、另一个随面改名，`--min` 由 81 同步到 80
  （`packages/dsh-notifier/package.json:9`）。
