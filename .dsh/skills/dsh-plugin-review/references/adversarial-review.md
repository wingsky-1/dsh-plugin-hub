# 对抗性评审手册（S5）

> 目的：协调者自产计划自带视角盲区；独立子 Agent 不带本会话先入之见，能更客观
> 挑错。**对抗评审 = S5 的强制步骤**（复杂方案必须先经对抗评审，这是工作方式约定，
> 不是可选项）。

## 1. 何时触发

- 落地计划（S4）产出后，实施前，**一律**先对抗评审。
- 用户显式要求「对计划进行对抗性评审 / 挑刺 / red-team」时，直接进入本阶段。

## 2. 派发（≥2 个独立子 Agent，并行后台启动）

两个视角互补，缺一不可：

### 视角 1「计划与交付」——排期/依赖/范围
任务自包含要点：
- 背景：五维评审的 P0/P1 清单摘要（引用来源，不要求子 Agent 重现评审）；
- 计划全文（含阶段、每项工时、依赖、门禁）；
- 挑刺维度：工时真实性（哪些项被低估——跨 host+client+测试的改动往往被低估）、
  隐藏依赖与次序错误（可并行被串行 / 必须前项的没写清）、遗漏项（新配置键的旧
  配置迁移、聚合 patch 重生成、版本策略、README 中英配对、真机验证缺设备时的
  替代策略）、范围蔓延/过度设计（哪些可砍）、最低可行切片（MVP 是什么）、
  风险前提（哪些假设可能不成立）；
- 输出：逐项问题清单（标题/理由/修正）+ 修正后的建议排期表 + 风险清单 +
  一句话「最该改的一处」。

### 视角 2 ｜技术路径——正确性/边界/安全/兼容
任务中要点：
- 让子 Agent 先读真实源码（绝对路径），对计划里**每一条实现路径**给
  「成立 ✅ / 有坑 ⚠️（坑在哪、怎么改）/ 不成立 ❌」判定；
- 特别拷问：平台编码（如 PowerShell 参数编码）、事件语义（waterfall 不短路、
  serial 无 next）、SSE/EventSource 行为、状态机与清理、跨标签协调、旧配置兼容
  （新增键时已有 dsh-*.json 的行为）、安全（webhook SSRF/令牌进日志/新路由围栏）、
  与仓库契约（干净模块/零依赖/patch 聚合）冲突、每条配套测试是否可自动化；
- 输出：逐项判定表 + 「若只做一件事」技术债 Top 5 与理由。

## 3. prompt 自包含要点（同 S2 规则）

- 给绝对路径与必读文件、给计划全文、给输出格式；声明「不客套，直接指出问题」；
- 视角 2 必须能把计划里的 `文件:行` 锚点与实际源码核对（行号漂移 → 指出）。

## 4. 汇总修正（协调者）

1. 收齐两视角后**逐条裁决**：有证据、可执行 → 采纳并改计划；重复/无据 → 说明不采纳
   理由；相互矛盾 → 以有源码/宿主证据者为准。
2. 输出「修正版落地计划」（用户可见的唯一版本），并附：采纳清单摘要 + 未采纳项
   （含理由）——体现「已过滤掉大部分错误的方案」。
3. 若对抗评审指出的问题牵涉评审结论本身（如某发现行号错误、某 P1 其实不成立），
   回 S3 修正总报告对应条目，再继续。

## 5. 常见对抗命中点（抽查自检）

- 排期低估（跨三端改动按单一文件估工时）；
- 遗漏「测试/验证投入」与「真机验证不可替代」；
- 新配置键引发旧配置漂移或 normalize 白名单破坏；
- 新路由/新接口忘记 loopback 围栏与 README 安全节；
- 客户端改动破坏干净模块契约（build-client 约束）或 CSS 硬编码色；
- 版本号与 README.zh.md 配对漏更新；
- 「远期」项误入近期版（范围蔓延）。
