# 模板集（S2 子 Agent prompt / 发现条目 / 聚合报告 / 落地计划）

## 1. 子 Agent 评审 prompt 模板（S2 直接填空使用）

```text
你是资深{角色名}。请对 {仓库/插件名} 做 {维度} 维度的深度评审（纯评审，不修改任何代码）。

## 评审对象（全部文件，逐行读）
- <绝对路径 1>（说明，如「宿主端，917 行」）
- <绝对路径 2>（客户端…）、<style.css / 脚本 / smoke / README / package.json / cordis.patch.yml>
- 对照规范/共享层：<仓库 AGENTS.md>、<shared/loopback.js / host-utils.js>、<pnpm-workspace catalog（@deepseek-ai/* 官方类型层）>

## 插件背景
<3-6 行：插件定位、事件接入、通道、安全边界、部署形态（Linux+局域网+三端）、
关键机制（如 60s 合并窗口、per-agent 状态机）>（让子 Agent 不必猜）

## 评审重点（维度
<从 dimensions.md 复制对应维的重点路径；必要时补「请与安装版 @deepseek-ai/dsh-* 源码交叉验证事件签名/枚举」>

## 输出要求（中文，Markdown）
- 逐条发现，每条固定格式：
  **位置**：文件 + 行号（精确）
  **严重度**：P0（阻断/正确性缺陷） / P1（重要，应修） / P2（一般） / P3（建议）
  **说明**：问题本质
  **证据**：引用关键代码片段
  **修复建议**：具体可操作
- 必须给：亮点 3-6 条、该维评分 0-100、优先级整改清单 Top N
- 纪律：基于真实代码逐行核实，不臆测；无法验证标注「未验证」；纯评审；
  最后一行方法学自评（哪些做过交叉验证、哪些只是推断）。
```

> 使用技巧：把 `{角色}` 换具体领域（代码评审专家/产品体验专家/多端适配专家/
> 插件架构师）；把「评审重点」段直接复制 dimensions.md 对应节，保证每个子 Agent
> 拿到相同尺度的答案集；DSH 宿主事件语义的断言提示分包写入，避免子 Agent 臆测。

## 2. 发现条目模板（统一全环）

```markdown
- **位置**：`src/index.ts:684-686`（文件:行，精确到函数/表达式）
- **严重度**：P1
- **摘要**：完成判定用黑名单，max-tokens 被误报为任务完成
- **证据**：`const NOT_COMPLETED = new Set(["aborted", ...])`；DSH 源码枚举含 max-tokens
- **修复建议**：改白名单 `COMPLETED_KINDS = new Set(["completed"])`，未知 kind 静默
```

## 3. 聚合总报告模板（S3 输出）

```markdown
# <插件名> 多 Agent 深度评审总报告

**评审对象**：<路径与版本>（宿主/客户端 CSS/脚本/测试行数）
**方法**：N 个独立上下文子 Agent 并行深评（<维度清单>）；协调侧独立佐证：
typecheck ✅ / smoke ✅ / 工作树干净 ✅

## 一、维度总览（六维 + 可选 G）
| 维度 | 子 Agent id | 结论一句话 | 评分 |

## 二、贯穿全部报告的主线（协调者提炼）
<根因级判断，如「服务器+局域网形态下核心卖点结构性断裂」——不是列表，是洞察>

## 三、跨维度交叉确认的问题清单（按严重度，★=≥2 Agent 独立确认）
| 级别 | ★ | 问题 | 位置 | 说明/校准 |

## 四、新功能路线图（聚合 C + 各维顺带发现）
| 功能 | 价值/成本 | 说明 | 否决项（为什么不做） |

## 五、安装影响结论（如做了 E）
双向评级 + 耦合面总表摘要 + 已到位防御

## 六、结论与下一步
建议动作 + 悬而未决（标注为未验证的项）
```

## 4. 落地计划模板（S4 输出）

```markdown
# <插件名> 落地计划：阶段排期与实施路径
**依据**：<评审交叉确认清单>；**人力**：<单人/多人假设>；**门禁**：<仓库门禁命令>

## 阶段 P0：认知对齐/文档（无风险）
| 项 | 路径 | 验证 |
## 阶段 P1：正确性与健壮性（逐项编号，含）：
- 路径（文件:行锚点 + 改动思路）
- 复杂度 / 工时
- 依赖（先行项）
- 测试（smoke 断言）与验收
## 阶段 P2：场景适配（多端/交互）
## 阶段 P3：新功能（分迭代，带回退校验）
## 阶段 P4：生态与远期（逐项单独 PR）

## 总时间线与里程碑
| 阶段 | 内容 | 工期 | 里程碑（版本） |
最终给「建议的下一步」。
```

## 5. 对抗评审补充消息模板（子 Agent 工具失效时）

```text
你的报告被截断/部分工具失效。请只基于你已读取的源码继续补完：1) <缺失段落>；
2) <缺失结论>；3) 无法验证的项明确标「未验证」。不要再跑 <失效工具>，
只用你已有的材料输出。
```

## 6. 评审交付物模板（重度评审：评审后进入实施时落成固定文件）

> 只对「评审后进入实施」的重度评审要求落成文件；quick 评审默认会话交付。
> 交付物仅两份（+ 共享检核表引用），不各自拆散；来源见 dsh-plugin-review
> 历次评审交付（样本随仓库演进，不再固守具体文件）。

### 6.1 REVIEW-AND-PLAN.md（评审结论 + 落地计划，交接物）

```markdown
# <插件名> 评审与落地计划

## 一、范围决策表
| 决策项 | 结论（做/不做） | 依据 | 用户裁量 |
## 二、评审结论（交叉确认清单 P0-P3，★=≥2 Agent 独立确认）
| 级别 | ★ | 问题 | 位置 | 证据类型 | 修正建议 |
## 三、落地计划（阶段排期，转实施 skill 用）
| 阶段 | 内容 | 工时 | 依赖 | 门禁 | 里程碑 |
## 四、专项方案/开放决策点（需更深评审或用户拍板的，含方案 v2 + 对抗评审结论）
| 专项 | 方案 | 对抗评审结论 | 开放决策点 |
## 五、进度记录（实施中更新）
```
