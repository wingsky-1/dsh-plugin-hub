# dsh-plugin-review — 多 Agent 深度评审插件方法论

把一次「5 子 Agent 并行深度评审 + 交叉验证 + 落地计划 + 对抗性评审」的完整流程固化：
评审目标必须是**只读**的——不修改插件代码、不改变工作树；产出物是评审总报告与
落地计划两条交付物，供用户确认后再进入实施。

## 0. 流程总览

```
S0 准备与基线 → S1 维度裁剪 → S2 并行子 Agent 评审 → S3 交叉验证与聚合
→ S4 落地计划 → S5 对抗性评审 → （可选）S6 报告沉淀 → S7 评审→实施交接（§8，评审后进入实施时）→ 转实施 skill
```

阶段号 S0-S7（正文节号 §）；S7 只在「评审结论获批进入实施」时走，平时评审止于 S6。
每阶段有明确的输入/输出与退出口；用户只追加一个维度（如「安装影响」）时，
从 S1 重新裁剪即可，不必重跑已完成阶段。生效的验证证据要按
`references/verify-checklist.md`（P0/P1 断言必须实测）。

## S0 准备与基线（协调者亲做，不委托）

1. **读规范基线**：目标仓库 `AGENTS.md`、`docs/DEVELOPMENT.md`（hub 仓）、
   目标插件的 `README.md`/`package.json`/`cordis.patch.yml`；记录仓库门禁命令
   （hub 通用门禁：`pnpm build && pnpm test && pnpm contract && pnpm pack:check`）。
2. **通读源码**：宿主端 `src/index.ts`、客户端 `src/client/index.ts`(+`style.css`)、
   系统脚本（如 `toast.ps1`）、`test/smoke.ts`；**记录每个文件的绝对路径与行数**，
   供子 Agent prompt 引用（行号锚点必须指向真实路径）。
3. **跑基线门禁**（只读、不改产物）：
   `pnpm typecheck`、`pnpm test`；`git status --short` 确认工作树干净。
   把结果写进总报告「佐证」节。
4. **建 todo**：准备 / 各维子 Agent / 交叉验证 / 计划 / 对抗评审 / 聚合各一项。
5. **标注边界**：确认本次为纯评审（只读）。若用户实际要「评审后直接改」，
   先完成评审与计划，改动另起会话按对应开发 skill 执行。

## 2. S1 维度裁剪（默认 6 维 + 可选维，按目标类型取舍）

默认矩阵见 `references/dimensions.md`（每维含审查重点 / 证据要求 / 输出要求）：

| 维度 | 何时必须 | 审查主体 |
|---|---|---|
| A 代码质量 | 任何 | 正确性/边界、类型、并发/资源、错误路径、安全、可维护性、测试质量 |
| B 功能体验 | 任何 | 触达有效性、文案、配置交互、噪声、权限策略、降级通道、诊断、缺口 |
| C 新功能方向 | 用户要增强 | 价值×成本、用户故事、实现要点、否决清单、路线图 |
| D 多端适配 | 插件带 UI/通知 | 窄屏/触控/iOS 差异/双主题/降级通道/宿主跨平台/验证矩阵 |
| E 安装影响 | 生态联动插件 | 被其他插件影响 + 影响其他插件（耦合面总表，双向） |
| F 安全专项 | 涉密钥/凭据/远端执行 | 威胁建模、注入面、SSRF、最小权限（可并 D 或独立） |
| G 开源/依赖复核（可选） | 用户要求「复用开源/自研核查/依赖治理」 | 自研 vs 成熟开源逐能力对照（能力×替代×成本×裁决表） |

**裁剪规则**：无 UI 的纯宿主插件省 D；单用户本机插件省 E；人力紧张时至少保留
A + B。用户点名维度时以其为准（如「增加安装影响分析」→ 只加 E；「自研核查」→
只加 G）。其余维度可中途增量追加（新增维度独立启动子 Agent、并入交叉验证，不重跑
已完成维）。
规模分级：**deep**（默认，5-7 维全跑） vs **quick**（用户只要 1-2 维时，
每维仍派独立子 Agent，但 prompt 允许只输出该维）。

## 3. S2 并行子 Agent 评审（核心编排）

### 3.1 角色分工

| 角色 | 执行者 | 职责 |
|---|---|---|
| 协调者 | 主会话 | 通读源码、写自包含 prompt、启动子 Agent、收集、交叉验证、聚合 |
| 评审子 Agent | 后台 subagent（每维度 1 个） | 独立读源码、独立出具带行号证据的结构化报告 |
| 对抗评审子 Agent | 后台 subagent（S5，≥2 个） | 对落地计划做红队挑刺 |

### 3.2 prompt 自包含要求（缺一不可）

每个子 Agent **看不到本会话上下文**，prompt 必须包含：
1. **绝对路径清单**：目标插件全部源码 + 仓库规范 + 共享层（如 hub 的
   `shared/loopback.js`、`types/dsh.d.ts`）+ 用于对照的同事插件。
2. **维度重点**：该维度的审查方向与证据要求的提示（复制 `references/dimensions.md` 对应节）。
3. **输出格式模板**（一并告诉它）：逐条发现格式固定为
   `**位置**（文件:行）/ **严重度**（P0-P3）/ **场景复现** / **证据**（代码引用）/
   **修复建议**`；另给：亮点 3-6 条、分值 0-100、Top N 整改清单。
4. **纪律**：基于真实代码逐行核实、不臆测；无法验证的标注「未验证」；
   纯评审、禁止修改文件；有能力核验 DSH 宿主事件语义时可对源码/安装版
   `@deepseek-ai/dsh-*` 交叉验证。
5. **明确跑跑后台**：全部 `run_in_background: true`，**一次消息并行启动全部**。

### 3.3 输出模板

见 `references/templates.md`（子 Agent prompt 模板 / 发现条目模板 /
聚合总报告模板 / 计划模板）。发现严重度定义：

| 级别 | 定义 |
|---|---|
| P0 | 阻断：主场景不可用 / 数据损坏 / 安全洞 |
| P1 | 重要：明显功能错、资源泄漏、声明-实现不一致 |
| P2 | 一般：局部体验/可维护性 |
| P3 | 建议：打磨项 |

**证据分级**：P0/P1 断言**必须给实测证据**（curl / 浏览器 MCP / node smoke，标注证据
类型，见 `references/verify-checklist.md`）；P2/P3 允许代码引用 + 标注「未验证」。
禁止只引代码推理定性 P0/P1（实测常推翻纸面结论，如 URL 长路径 431@~16KB 边界）。

### 3.4 并行纪律

- 全部子 Agent 独立上下文、互相不读彼此输出（防共谋偏置）。
- 协调者在等待期间做**独立佐证**（跑门禁、看 git log、核对产物与源码同步），
  不忙轮询；子 Agent 完成有系统通知。
- 若某子 Agent 工具链中途失效（如 bash ENOENT），协调者给它发补全消息只补缺失
  部分，或把「未验证」标注带进聚合——**不重复重试 >2 次**，不阻塞整体。

## 4. S3 交叉验证与聚合

1. 逐个收齐子 Agent 报告（先到先收，全部到齐才聚合）。
2. **交叉验证**：同一发现被 ≥2 个独立子 Agent 提出 → 在总清单该项打 **★**；
   相互矛盾时以「有源码/宿主证据 + 行号」者为准，协调者在总报告中写明裁决理由。
3. **聚合总报告结构**（模板见 `references/templates.md`）：
   - 总览表（维度/子 Agent id/结论一句话/评分）
   - **主线判断**（贯穿多份报告的根因，如"部署形态与服务定位错位"——这是总报告
     最有价值的一节，协调者必须自己提炼，不照抄）
   - 跨维度交叉确认清单（P0-P3，★ 标记）
   - 新功能路线图（聚合 C 的候选 + 其他维度顺带发现）
   - 安装影响结论（E 时）
   - 结论与下一步（直接服务用户决策）
4. 汇总稿必须**经协调者自己根据源码做规则性抽查**（如子代理引用的行号是否成立、
   重要断言是否与通读的源码一致），不做「照单全收」。

## 5. S4 落地计划（把发现改为可执行排期）

1. 阶段式排期：**P0 认知对齐/文档 → P1 正确性修复 → P2 场景适配 →
   P3 新功能 → P4 生态/远期**；每项：路径（文件:行锚点、改动思路）、
   工时（S/M/L 或天数）、依赖（哪些项必须先行）、验证方式、门禁。
2. 明确**每阶段收尾的验收门禁**与**发布资源**（如 0.x 语义版本策略）。
3. 计划交用户确认后再实施（遵守「方案优先于实现」的工作方式约定）。

## 6. S5 对抗性评审（强制，对落地计划）

1. **为什么**：协调者自产计划自带视角盲区；独立子 Agent 不带先入之见能挑错。
2. **派 ≥2 个并行对抗子 Agent**（模板见 `references/adversarial-review.md`）：
   - 视角 1「计划/交付」：排期真实性、依赖次序、遗漏（配置迁移/聚合 patch/版本/
     README 配对/验证矩阵）、残余项、范围蔓延、最低可行切片。
   - 视角 2「技术路径」：逐项实现思路是否正确/有坑（平台编码、事件语义、兼容、
     安全边界）、与既有契约的冲突、测试可测性、过度设计信号。
3. **汇总修正**：只吸收「有证据、可执行」的挑刺并说明取舍；把过滤后修正版
   计划再呈现给用户（「已过滤掉大部分错误」的版本）。

## 7. S6（可选）报告沉淀

- 默认在会话交付即可；用户要求落库时生成 `docs/REVIEW-<插件>.md`
  （或经 `technical-documentation` 规范瘦身）。
- 报告内保留每一子 Agent 的名目与结论摘要，方便回溯与后续逐个整改。
- **重度评审**（评审后进入实施）建议按 `references/templates.md` 的「评审交付物」
  节落成 `REVIEW-AND-PLAN.md`（范围决策 + 阶段计划 + 专项方案/决策点）与
  `TECH-DEBT.md`（已清偿/遗留/勾选/自研对照）；quick 评审默认会话交付，不强求落库。

## 8. S7 评审→实施交接（指针，不内联实施细节；仅获批进入实施时走）

- 计划获批进入实施时：**转入 `dsh-plugin-hub-dev` 按实施 skill 执行**；
  交接物为 `REVIEW-AND-PLAN.md`（含阶段计划与决策点）。
- commit-only / 阶段门禁 / 运行时确认 / 实施常见坑等**实施细节归实施 skill**，
  本 skill 是纯只读评审，不内联（见 `references/workflow-common.md` §1/§3/§5）。
- **实测验证证据**（P0/P1 断言必须实测）按 `references/verify-checklist.md` 执行。

## 9. 交付与纪律检查

- **不修改代码**：纯评审阶段零写操作；必须「改」时先回用户确认再转开发 skill。
- **全中文**：评审报告、总报告均中文（代码/专名保留原文）。
- **门禁证据**：报告含协调者独立验证结论（typecheck/test 通过/产物同步/工作树状态）。
- **完成**：总报告 + 落地计划（+ 修正计划）交付 → 本 skill 完成；单轮只做「评审」
  时以总报告 + 路线图为终。
