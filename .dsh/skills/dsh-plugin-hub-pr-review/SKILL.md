# dsh-plugin-hub-pr-review — hub 仓 PR 评审方法论

把一次「PR 基线获取（worktree 拉起）→ 门禁实证 → 多维审查 → 子 Agent 对抗评审
→ P0/P1 亲自复现 → 分级结论 → 三桶分诊 →（经确认）PR 评论 + follow-up + issue
跟踪」的流程固化。
核心立场：**门禁绿 ≠ 无 bug**（CI pass 与本地全绿都可能被弱断言掩盖真实缺陷），
评审结论必须建立在「源码行号证据 + 关键断言运行时复现」之上。

## 0. 流程总览

```
S0 PR 基线（含 worktree 拉起） → S1 门禁实证 → S2 多维审查（协调者亲做）
→ S3 子 Agent 对抗评审 → S4 交叉验证与复现 → S5 分级结论报告
→ S6 三桶分诊 → S7 外发：PR 评论 + follow-up + 遗留清单（可选，须用户确认；
  遗留汇总 issue 在合并时统一创建）
```

## 与 dsh-plugin-review 的分工边界

- `dsh-plugin-review`：面向**整插件**的 5-7 维并行深评，规模大一个量级。
- 本 skill：面向**单个 PR 的 diff**，以合并门禁视角做**变更聚焦评审**，
  实证纪律更严——PR 声明了什么就要核什么。
- 两者可混合执行，升级/降级判据见下节「规模分级」。

## 规模分级（升级与降级判据）

**基线编排**：1 个上下文独立的对抗子 Agent。

**升级判据（满足任一即升为多维并行）**：
- changedFiles 跨 ≥2 个插件包，或 diff 触及聚合包 `dsh-plugins-all`
  邻接面 / README 含退役声明；
- PR 属迁移/退役型（包级退役、版本窗口期、生态联动处置）。

升级后复用 `dsh-plugin-review` 的多维并行编排（按维度拆分子 Agent），
但本 skill 的以下纪律**不可省**：S1 门禁实证、S4 P0/P1 运行时复现、
S6 三桶分诊。混合时先统一严重度标尺（见 S3 模板），避免两套标尺人工对齐。

**降级判据（小 PR 减配边界）**：
- **可以减**：子 Agent 数量（极小 diff 可并入协调者自查 + 1 轮对抗）、
  S5 报告弹性（未验证项写「无」一行带过、对账表可与门禁记录合并）。
- **永不能减**：P0/P1 运行时复现、外发双确认、S2-G 红线速查、纪律检查节。

**多维并行时的评分口径**：各维打分仅作维度间严重度排序参考，
总报告不计算加权平均——最终交付物是 S6 分诊 + 单一合并结论，
驱动结论的是必修项的成本-收益，不是分数。

**中途接入对账**：本 skill 可能在评审进行到一半时才被加载（触发词后置等）。
此时不从头重做，逐条核对 S0-S4 已完成项、补缺后再继续。
典型缺口：门禁只跑了部分、worktree 位置/清理不合规范、误建了本地分支。

## S0 PR 基线（协调者亲做）

1. **取 PR 元数据**：
   `gh pr view <N> --repo wingsky-1/dsh-plugin-hub --json title,body,state,baseRefName,headRefName,additions,deletions,changedFiles`
   ——通读 PR body，**逐条记下它声明了什么**（改了什么、测了什么、兼容性承诺），
   后面 S1/S4/S5 要逐条对账。
   **关联 issue 对账**：body 含 `Closes #N` 时取 issue 全文对照；PR 方案
   **偏离 issue 提案**时，评估偏离论证是否扎实，并在报告/评论中给出
   「是否需在 issue 下留言说明理由」的建议（偏离合理但 issue 侧无说明 = 流程缺口）。
2. **变更文件清单**：`gh pr diff <N> --name-only`；按
   宿主端 `src/index.ts` / 契约与共享层 / 客户端 `src/client/` / 测试 /
   文档（README 中英）/ 构建配置（package.json、pnpm-lock、shared/）分组，
   形成阅读计划。同时据此判定规模分级（上节），确定子 Agent 编排。
3. **拉起 PR 到独立 worktree**（不动主 clone 的工作树，又能在 PR 代码上
   实跑门禁与复现脚本）：
   ```sh
   # 取 PR head（无需知道分支名；在仓库工作树内执行，或用 git -C <仓库根>）
   git fetch origin pull/<N>/head
   # 建 worktree（建在仓库同级目录 ../，不污染仓库自身工作树）
   git worktree add ../dsh-hub-task-<n> FETCH_HEAD
   ```
   - **禁止** `fetch origin pull/<N>/head:<branch>` 写法——会建本地分支；
     若已建，收尾清理清单须含 `git branch -D <branch>`。
   - **依赖策略**：worktree 内先**直接试跑门禁**（本仓构建脚本自包含，
     常态下无需安装）；因缺依赖失败再 `pnpm install --frozen-lockfile`。
     复现脚本按 S4 三档选档，仅第二档需要先 build。
   - 主 clone 若恰好已检出该分支也可直接只读审（先 `git status -sb` 确认），
     但门禁与复现仍建议在 worktree 做，避免污染主 clone 的未跟踪文件。
   - **评审收尾清理**：`git worktree remove ../dsh-hub-task-<n>`
     （有未跟踪产物时加 `--force` 前先确认无价值文件）；
     需要留证据时先把复现脚本/输出拷到 /tmp 等仓库外目录再清（见 S4 落盘约定）。
4. **读规范基线**：仓库根 `AGENTS.md`（门禁命令、全局约定、提交规范、测试纪律、
   发布纪律）；目标包的 `README.md` + `package.json`。
   **仓库惯例先行核对**：flag「版本号未 bump / release-notes 缺失 / 提交不规范」
   前，先 `git log -- <path>` 核对该仓惯例，防止假阳性发现混入报告
   （如版本号由独立 release 提交统一处理是惯例而非缺陷）。
5. **建 todo**：基线 / 门禁实证 / 读 [references/checklists.md](references/checklists.md) / 源码通读 /
   安全面 / 兼容与割接 / 测试与文档 / 门禁实跑 / 子 Agent 对抗评审 /
   分诊与汇总报告，各一项（「读 checklists.md」是 S2 的硬前置，见下节）。

## S1 门禁实证（先跑起来，再读码）

1. **本地实跑全量门禁**（后台执行，期间继续 S2 读码）：
   `pnpm build && pnpm test && pnpm contract && pnpm pack:check && pnpm typecheck`。
   PR body 声明「全门禁绿」时必须亲自复核，不能只信 CI。
2. **后台 job 输出收集用 marker 检查法**：全量门禁输出数千行，
   以各阶段成功标记 + 最终 exit code 为准确认，不逐行读。
3. **CI 对照**：`gh pr checks <N> --repo wingsky-1/dsh-plugin-hub`。
4. **记录反差**：门禁结果与 PR 声明的差异（如某门禁未跑、某断言跳过）写进报告。
5. 记住结论模板：**门禁绿只能证明「没崩」，不能证明「行为正确」**
   （弱断言可以同时骗过本地门禁与 CI）。

## S2 多维审查清单（协调者亲做，diff 聚焦）

> **第 0 步（硬前置）：read [references/checklists.md](references/checklists.md)，未读不得开始通读 diff。**
> 该文件含 A-F 六维详表 + 三个专项清单；本节只留索引。跳过它 = 盲区评审。

按以下维度通读 diff 全量文件（不是只看 diff 片段——要读改动文件的完整现状）：

| 维度 | 一句话要点 | 详表 |
|---|---|---|
| A 正确性与边界（最高优先） | 竞态三件套 / 热重载单例 / 迁移割接逐步走查 / 数值边界 / 新调用路径×既有函数交叉影响 / 防御对称性 | [checklists.md](references/checklists.md) |
| B 安全面（hub 红线） | 围栏+方法校验 / 动态执行信任级 / 脱敏出口全覆盖+绕过抽样 / 信息暴露 | [checklists.md](references/checklists.md) |
| C 兼容与数据 | 旧配置缺键不退化 / 数据割接语义 / peer externals | [checklists.md](references/checklists.md) |
| D 文档-实现一致性 | 配置键逐一对照 / 命令路径默认值 / 中英配对 / 改动命令先对照 main 定性 | [checklists.md](references/checklists.md) |
| E 死代码与一致性 | 无消费配置键 / 未使用变量 / 无调用方导出 / 变量遮蔽 | [checklists.md](references/checklists.md) |
| F 测试质量（假绿识别） | 弱断言 / bundle 字符串断言 / 时序 sleep / 精确计数往返 / 性能护栏输入形态假绿 | [checklists.md](references/checklists.md) |

**三个专项清单按触发条件加载**（均在 [checklists.md](references/checklists.md)）：
- diff 含正则/脱敏类改动 → 清单一「正则/脱敏类 diff」；
- 改动任一插件包 → 清单二「聚合包/生态联动」（hub 仓特有，必查）；
- PR 属迁移/退役型 → 清单三「迁移/退役型 PR」。

### G. 仓库红线速查（任一命中直接列入报告）

禁 emoji（代码/注释/文档/UI/提交信息，含 ★✅⚠️ 等符号装饰）｜
客户端干净模块（禁手写 load/IIFE/`__DSH_PLUGIN_ID__`）｜样式独立 CSS +
`--dsw-alias-*` 主题变量双主题｜构建预设只用 build-client.ts｜
patch id 规范 + 改独立包 patch 后重生成聚合 patch｜Conventional Commits｜
发布物不含 src//test//内部文档｜内部治理文档不应推公开仓。

## S3 子 Agent 对抗评审（强制一轮）

1. **派上下文独立的对抗子 Agent**（run_in_background: false，等结果；
   数量按规模分级），prompt 自包含，模板骨架：
   - 仓库绝对路径、分支与 base、PR 一句话概述、主要文件清单；
   - 审查方向提示：S2 七维要点 + 本 PR 触发的专项清单条目；
   - **统一严重度标尺**：按本 skill 的三级（严重/中等/轻微）输出，
     每条附文件:行号依据；会导致错误行为的断言必须附**可重跑的实测命令**，
     不自行发明四级标尺（避免汇总时二次换算）；
   - **复现脚本交接约定**：把严重级断言的复现脚本留存到约定目录
     （如 `/tmp/pr<N>-exp/`），脚本头部自描述（目的/前提/预期输出）；
     协调者在 S4 直接重跑坐实，而非从零重写；
   - 输出格式：三级问题列表 + 总体结论「可合并/需修改」；
     要求它**只报有代码依据的真实问题**。
2. **多维并行时预置共同交叉项**：把最可能有争议的机制性问题
   （如装配顺序行为、迁移等价性）同时布置给多个相关维度独立验证，
   为 S4 制造独立确认；协调者在等待期做自己的独立佐证形成第三方意见。
3. **双向价值预期**：子 Agent 会抓到协调者通读时的盲区，也会产生误报——
   所以进入 S4。等待期间协调者继续完成 S2 未完维度，不忙轮询。

## S4 交叉验证与复现（P0/P1 断言必须亲自复现）

1. **子 Agent 报告的每个严重/中等问题，协调者逐条回到源码核实行号与逻辑**；
   相互矛盾时以「有源码证据 + 行号」者为准。
2. **所有 P0/P1（会导致错误行为的）断言必须运行时复现**——无论来自
   子 Agent 报告还是协调者自查，不允许纸面定性。
3. **复现三档选档准则**（先按问题类型选档，不要默认上最重的第三档）：
   - **第一档 · 纯函数直测**：脱敏/格式化/解析类导出纯函数，
     Node ≥24 原生 type stripping 直跑 .ts 源码即可
     （`node --input-type=module -e "await import('/abs/path/src/x.ts') ..."`），
     零构建成本。若失败，**先排查是否触到 strip-types 语法限制**
     （enum/namespace/parameter properties 等需转换语法、tsconfig paths 不生效），
     再降第二档——勿把工具限制误判为代码问题。
   - **第二档 · build 后直跑 lib**：实例级行为（模块内状态、生命周期），
     先确保门禁 build 过，再直跑 `lib/index.js` 导出的实例/函数。
   - **第三档 · fake ctx + 路由注入**：路由级行为与围栏交互。
     fake ctx 用 webServer.register 收集路由、effect 立即执行、注入 fetchImpl、
     mkdtemp 临时目录模拟旧数据文件。注意：fake req 要带
     `socket.remoteAddress`/`headers.host`/`sec-fetch-site`
     （否则被 loopback 围栏 403，得出假阴性）；async handler 要 await；
     ESM 动态 import 用绝对路径。
4. **复现证据落盘**：P0/P1 的复现脚本与输出摘要落盘到评审交付目录
   （如 workspace 下 `pr<N>-review/`），脚本头部自描述——会话结束与
   worktree 清理后第三方仍可复核；然后再清 worktree。
5. 复现**推翻**子 Agent 结论时同样写进报告（标注「复现未成立+原因」）；
   复现**坐实**时保留复现命令与输出摘要作为证据。
   **复现失败先怀疑自己的验证路径，再下「误报」结论**——换验证角度
   （如内存态 vs 已落盘态、是否等待异步持久化时机）后再定性。

## S5 分级结论报告

结构固定（小 PR 适用弹性条款）：
1. **总体评价**（架构方向、亮点、一句话立场）。
2. **严重问题**（会导致错误行为，附复现证据）——逐条：现象、根因（文件:行）、
   复现结果、修复建议。
3. **中等问题**（边界/维护隐患）——表格：# / 问题 / 依据（文件:行）。
4. **轻微问题**（风格/文档/死代码）——列表。
5. **各维度小结**（正确性/安全/性能资源/兼容/测试/门禁，各一两句）。
6. **PR body 声明对账表**：声明 / 属实·不属实·无法验证 / 依据，
   逐条闭环（弹性：小 PR 可与门禁记录合并呈现）。
7. **未验证项汇总**：各维散落的「未验证」标注汇成单一清单，
   注明「哪条结论依赖哪个未验证前提」，供后续 issue 或人工验证认领
   （弹性：无未验证项时一行「无」带过）。
8. **结论**：`可合并` / `建议修改后合并` / `需修改`，明确「必须修」与
   「强烈建议修」清单及最低修复成本估计。

## S6 三桶分诊（评审结论的落地形态）

把 S4 坐实的发现按处置方式分成三桶，**分诊标准先于情感**：

**桶① 代码必修（阻断合并）**——满足任一：
- 会导致错误行为且已复现（数据损坏/重复/丢失、状态错乱、竞态回填）；
- 安全面缺口（围栏缺失、脱敏出口遗漏、未交代的动态执行信任级）；
- 在宿主主线程同步路径引入 O(n²)/回溯退化（DoS 面）；
- 文档-实现脱节会直接坑到照文档操作的用户（配置键名错误类）；
- 仓库红线命中（emoji、干净模块契约破坏、围栏缺失等不可让步项）。

**桶② 合并前 follow-up 落盘**——不阻断代码合并，但必须在 PR 评论/
merge commit 中书面承诺的后续动作：
- 发版顺序、deprecate 时机、关联包同批处置等治理项；
- 版本窗口期的文档失实修正（发布物版本落后于文档宣称行为）；
- 需要「紧随 PR 执行」但不属于代码缺陷本身的动作。

**桶③ 遗留汇总（记录在 PR 评论，合并时统一开一个跟踪 issue）**——满足任一：
- 边界/维护隐患但当前行为正确（死代码群、弱类型 shim、变量遮蔽、
  fire-and-forget 乱序等低概率时序）；
- 弱断言/测试改进（不掩盖已知严重问题的前提下）；
- 文档打磨（描述措辞、示例目录随包发布、peer 版本宽窄）；
- 设计取舍类，需要讨论而非直接改；
- 「侥幸正确」的隐式机制缺注释固化；
- PR 偏离 issue 提案且 issue 侧无说明（流程缺口）。

每桶逐条给：根因锚点（文件:行）、一句话修复思路、验证方式。
分诊结果先呈用户确认，再进入 S7。

## S7 外发：PR 评论 + follow-up + 遗留汇总 issue（可选；**发出前必须经用户明确确认**）

1. **PR 评论** = S5 报告精简版，结构固定：
   - 总体评价（一两句，肯定架构方向与亮点在前）；
   - 必须修清单（严重问题带复现证据与文件:行，逐条给修复建议）；
   - 中等/轻微问题表格；
   - **follow-up 承诺段**（桶②逐条：动作 + 时点，作为书面承诺）；
   - **遗留清单段**（桶③逐条：现象 / 根因（文件:行）/ 修复建议 / 验收标准，
     作为合并时汇总 issue 的底稿）；
   - 结论（`需修改后合并` 等）+ 「遗留项将在合并时汇总为单一 issue 跟踪」预告。
   正文先落本地文件（如 `pr<N>-review-comment.md`）供用户过目，
   确认后 `gh pr comment <N> --body-file <file>` 发出。
2. **follow-up 跟踪关闭**：桶②各项由提出方在后续 PR/issue 中跟踪关闭；
   需要独立跟踪的转 issue 并在评论中引用形成闭环。
3. **遗留汇总 issue**（评审阶段**不**逐条开 issue；待 PR 合并时统一创建
   **一个**跟踪 issue，收录全部遗留项）：
   ```sh
   gh issue create --repo wingsky-1/dsh-plugin-hub \
     --title "chore(dsh-<pkg>): PR #<N> 评审遗留项汇总" \
     --body-file <issue-body.md> --label "tech-debt"
   ```
   - issue 正文模板：来源（`From review of #<N>`）/ 遗留清单 task list
     （逐条 `- [ ]`：现象 / 根因（文件:行）/ 修复建议 / 验收标准，
     完成一项勾一项）/ 处置优先级建议；**不逐条拆分为多个 issue**。
   - label 无 `tech-debt` 时先 `gh label list` 核对，用仓库已有标签或注明建议新建。
   - 创建后在 PR 评论补一句引用形成闭环（`tracked in #<m>`）。
4. 用户说「先不提」时止步于 S5/S6 交付，评论与 issue 草稿备好待发。

## 纪律检查

- **只读评审**：S0-S5 零写操作（DSH 配置、远端均不动；worktree 内只跑门禁与
  复现脚本，不提交、不 push）；复现脚本落盘到约定的评审交付目录，不留痕于主 clone。
- **worktree 收尾**：评审交付后 `git worktree remove` 清理（见 S0 第 3 步），
  若误建了本地分支一并 `git branch -D`；不在仓库同级目录残留
  `dsh-hub-task-<n>` 目录。
- **不关闭/重启 dsh web 进程**；门禁实跑用后台 job，等待期做独立佐证。
- **全中文**报告与评论；代码/专名保留原文。
- **对账闭环**：PR body 的每条声明（测试清单、兼容性承诺、门禁声明）
  在报告中都有「属实/不属实/无法验证」的对应结论。
- **外发双确认**：PR 评论、follow-up 承诺与遗留汇总 issue 都属外发动作，
  逐批经用户确认后执行；用户叫停时止步于本地草稿。
