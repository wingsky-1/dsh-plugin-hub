# 提案：跨包共享机制的演进（`shared/` 与 core 包）

> 状态：**提案，未批准**。本文件用于记录方向、判据与前置调研，不构成实施承诺。
> 相关：[架构治理方法论](../ARCHITECTURE-METHOD.md) 第 4 章「共享机制四层选型」。

## 1. 背景

插件族当前的跨包共享只有一种机制：仓库根 `shared/`，以「构建期源码依赖」形态被各包
相对路径 import，由 esbuild 内联进各包产物。现状实测：

| 事实 | 数值 |
|---|---|
| `shared/` 代码模块数 | **9**（7 个宿主 `.js` + 2 个客户端 `.js`），另有 1 个纯声明文件与说明文件，目录合计 20 个文件 |
| 消费方 | 4 个插件包（另有一个模块生产消费已退役、测试仍引用） |
| 单包复用面（引用到的模块数） | 通知插件 6、MCP 管理器 9、用量统计 6 |
| 载体形态 | `.js` + `.d.ts` 双写（受编译产物根目录约束，实现不可 TS 化） |
| 引用方式 | 跨包相对路径（`../../shared/x.js`） |
| 已知漂移 | `shared/sse-hub.js` 已有两个消费方，但未登记在 `shared/README.md` 的模块表中 |

也就是说：**共享机制本身已经在高强度使用**，本提案要讨论的不是"要不要共享"，
而是"用哪种机制共享"。

## 2. 三种机制的分工

| 机制 | 解决什么 | 不解决什么 |
|---|---|---|
| `shared/`（现状） | 轻量、稳定的跨包工具函数与类型 | 类型漂移（双写）、路径稳定性（相对路径随包内搬迁碎裂）、独立版本与测试工程化 |
| core 包（本提案） | 同上 + 工程化：TS 源码直出、包名引用、可独立测试与版本化 | **共享实例**（发布物自包含 + 构建期内联，必然每包一份副本） |
| cordis 服务面 | **跨插件运行时单实例**：状态、注册表、连接池 | 编译期类型与纯函数复用 |

结论性判据：**需要共享状态就用服务面，需要共享代码才考虑包**。把可变状态放在模块级
导出上，在内联发布模型下不会真正共享，只会制造"看起来是单例"的陷阱。

## 3. 什么内容才够格进 core 包

沿用并加严 `shared/` 的准入规则，核心是**"已被重复实现"而非"可能被复用"**：

1. **≥3 个稳定消费者**（比 `shared/` 的 2 个更严，因为包一旦发布很难回收）。
2. **已被 2 个以上包以近似重复形态各自实现**（这是核心判据：先有重复，再有抽象）。
3. **无包级常量依赖**；包差异经参数化或薄 facade 注入。
4. **边界清晰**：core 不得依赖任何插件包（依赖方向单向）。
5. **有独立测试与版本策略**；发布物仍自包含（构建期内联，不作为运行时 npm 依赖分发）。
6. **登记消费方与行为契约**。

按此判据，**当前没有经过实测的合格候选**——必须先做重复度调研（见第 5 节），
不接受"看起来会重复"的推断。

## 4. 收益与成本

收益：

- 消除 `.js` + `.d.ts` 双写带来的类型漂移面（有门禁兜底，但仍是维护负担）。
- 引用从跨包相对路径改为包名，包内目录搬迁不再碎裂引用。
- 共享代码获得完整的工程化待遇：独立 tsconfig、独立测试、独立变更记录。

成本与红线：

- **新增包是仓库级变更**：触发聚合包校验与 npm 布局校验，且包命名、聚合 patch 生成、
  版本一致性策略都要同步。
- **构建链需要显式支持**：从 workspace 包内联进各包产物；这是对现有构建脚本的改造，
  属跨包共享脚本的仓库级改动。
- **发布物自包含不变**：内联即分发副本，第三方许可归集链路要覆盖 core 包内容。
- 若不解决"双写"的动机而只是搬家，则收益为零、成本为正——**必须先有重复度实测**。

## 5. 前置调研（实施前必须完成）

1. **重复度实测**：对 3 个以上包逐一比对"近似能力"的实现（连接管理、设置桥接、
   路由守卫、客户端设置卡片模式、事件订阅脚手架等），给出逐项的行级重合评估。
   判据：同一能力在 ≥2 个包中各有实现，且语义等价、差异可参数化。
2. **迁移成本评估**：受影响文件数、引用改写量、回归面（这些包都有强制门禁）。
3. **工程化收益量化**：双写漂移的历史事故数、相对路径引用碎裂的历史次数。
4. **构建链方案**：内联实现方式、许可归集、包体积影响、与现有发布物断言的关系。

## 6. 建议的推进方式

- **短期（当前重构周期内）**：不动。继续按 `shared/` 既定准入规则使用；
  新的包内共享一律走 `types/` 与 `utils/`（方法论第 3 章四级判据）。
- **中期**：以某个包的重构为试验田，验证"包内共享层"判据的实际效果；
  同时完成第 5 节的重复度调研。
- **长期**：调研结论支持时，core 包作为**独立 tracking issue + 本文件第 5 节前置调研**
  推进（需维护者批准，属仓库级红线）；结论不支持时，把结论回写本文件并归档，
  避免同一议题反复讨论。

## 7. 与其他方向的关系

- 包内共享（`types/` / `utils/`）与 core 包是**不同层级**的问题，不互相替代。
  前者解决"包内跨模块"，后者解决"跨包骨架"。
- `shared/` 与 core 包在可预见期内**并存**：前者是轻量工具层，后者是骨架层。
  若未来 core 包成熟，可评估把 `shared/` 中的骨架型模块迁入 core，
  工具型模块保留原地。
