# 架构治理方法论

> 适用范围：dsh-plugin-hub 各插件（cordis bundle 包），可迁移至其他 cordis 插件。
> 本方法论的每条原则都锚定真实实测案例，案例来源见 [dsh-notifier 整改计划](../packages/dsh-notifier/docs/refactor-plan-690.md)。
> 定位：指导结构重构的实施，以及重构完成后的长期维护。

## 1. 四条第一性原则

1. **先修尺子，再动结构。** 度量口径失效时，任何结构搬迁都会得到"门禁全绿但约束归零"的结果。
   *案例*：`verify-dir-imports` 的目录集合只取 `src/` 顶层一层，一旦引入分组层，8 个域的
   跨域引用全部被判为"同目录"，值边从 10 条降为 0 条，而门禁**仍然打印 PASS**。
2. **边界先于结构。** 域边界与依赖方向是本质，目录对称是表象。不能为目录美观牺牲约束力。
3. **共享层是稳定抽象，不是杂物间。** 共享面越大，暴露面越大、耦合力越强；
   把符号搬进共享层会让它从"某域的实现细节"变成"人人可依赖的公共面"。
4. **未被机器强制的约束等于不存在。** 纸面规则不构成约束。
   *案例*：39 处"实现文件跨域引用他域门面"在规则收紧后成为存量，但在门禁落地前
   没有任何工具在看它们。

## 2. 六个载体的职责与依赖方向

| 载体 | 职责 | 允许的依赖 |
|---|---|---|
| `<域>/interface.ts` | **入口**：本域对外承诺（下游从这里进） | 本域实现；他域 `interface.ts`（优先 type-only） |
| `<域>/deps.ts` | **出口**：本域对上依赖的注入面声明（`XxxDeps` / Ports 类型物理定义处） | 他域 `interface.ts` |
| `<域>/<impl>.ts` | 本域内部实现（单元测试白盒直连） | 本目录内 + 本域 `deps.ts` |
| `types/` | 多模块共用**类型**（type-only、零运行时） | 零依赖 |
| `utils/` | 多模块共用**函数与常量**（纯、无状态、零 node 依赖） | 零依赖 |
| `index.ts` | 组合根：装配 + 包导出面 | 全部域 `interface.ts` |

铁律：

- `impl` 引用本域 `interface.ts` **不得取值**（只允许 `import type`）——取值会形成
  `impl → interface → impl` 的表观环。*案例*：某域实现文件从本域门面取一个常量，
  而门面又从该实现 re-export 工厂函数，构成文件级值环；模块粒度门禁看不见它。
- 跨域**运行时能力一律经 `deps.ts` 注入**，不直接引用他域实现。
- 分组层（如半区目录）必须对门禁透明：模块粒度取**叶子**（递归含 `interface.ts` 的目录），
  分组层本身不参与依赖图。

## 3. 共享层准入四级判据（顺序不可颠倒）

| 序 | 问题 | 判定 |
|---|---|---|
| 1 | 有明确的**领域所有者**吗？ | 有 → 留原域 `interface.ts`；他域经**本域 `deps.ts`** 声明依赖。这是「依赖」，不是「共享」 |
| 2 | 消费关系**合理**吗？（本域正当需要，而非越权、图方便、绕过注入） | 不合理 → **先修消费方**（收窄类型、加映射层、改注入），不搬符号 |
| 3 | 概念性质是**公共语言/协议**吗？（无归属、跨端、稳定、不随某域模型漂移） | 否 → 回到第 1 条 |
| 4 | 零依赖 + ≥2 个**正当**消费者 | 才进 `utils/`（函数/常量）或 `types/`（type-only） |

三种反模式：

- **越权依赖实现细节**：某域只需要"标识集合"，却 import 了对方的整张文案表。
  正确做法是提取最小事实源或经注入获取判定能力，而不是把文案表变成公共面。
- **用共享掩盖缺失的防腐层**：某域直接吃另一域的配置模型类型，被对方的模型演进绑定。
  正确做法是本域定义窄类型，由调用方做映射。
- **提前抽象**：单一消费者就下沉共享层。共享层成员越少越稳定。

判据的反向效果：严格执行后，`types/` 的成员往往**极少甚至为空**——这是
「减少暴露面与耦合」的正确结果，绝大多数跨域关系应当表达为 `deps.ts` 的
**依赖声明 + 注入**。

## 4. 共享机制四层选型

按「跨什么边界」选择机制，不要用一种机制解决所有问题：

| 层 | 边界 | 机制 | 准入 | 关键限制 |
|---|---|---|---|---|
| 1 | 包内跨模块 | `types/` + `utils/` | 第 3 章四级判据 | 零依赖、零 node 全局 |
| 2 | 跨包轻量工具 | `shared/`（构建期源码依赖） | ≥2 稳定消费者；无包级常量依赖；独立测试；消费方登记 | `.js` + `.d.ts` 双写；相对路径引用，包内搬迁即碎 |
| 3 | 跨包**架构骨架** | **core 包**（候选，见 [提案](proposals/core-package.md)） | 比 `shared/` 更严：≥3 消费者；已被 2 个以上包以近似重复形态实现；有独立测试与版本策略 | 新增包为仓库级变更；发布物仍须自包含（构建期内联） |
| 4 | **运行时单实例** | cordis 服务面（`ctx.provide` / `ctx.get`） | 需要跨插件共享状态时**唯一**正确机制 | 模块级共享在内联模型下必然是每包一份副本 |

注意第 3 层与第 4 层的分工：core 包解决**工程化**问题（类型不漂移、路径稳定、
可独立测试与版本化），**不解决共享实例**问题。把状态放在模块级导出上，
在各包内联的发布模型下不会真正共享。

## 5. 开闭原则的量化方法

对每个可扩展维度盘点「新增一项要改几处」，**超过 3 处即判违反开闭原则**。

*案例*：新增一个内置事件 kind，需要在 7 个源文件（宿主 5 + 客户端 2）中同步约 12 张
独立的表或分支（文案表、强度映射、配置字段、默认值、配置键清单、校验器、提示文案、
归一化分支、免打扰豁免、客户端开关表、kind 映射表、双语字典）。
**计数口径**：按"必须修改的表/分支"计数，不按命中的关键字行数计——口径不同会得出
差异很大的数字，写进验收判据时必须一并写明。
新增一个频道类型约 9 处；新增一个配置键 7 处。

目标形态：**单点注册 + 派生**，且跨端共用同一张表（避免两端各写一份）。

量化动作：新增维度前先数同步点，重构后重数一遍，把数字写进验收判据。

## 6. 暴露面与耦合收敛

- **包导出面三层裁定**：安装面（`name` / `apply` / `inject` / 路由常量）、
  配置面（配置类型与默认值）、契约面（对外 ABI 与服务面类型）。不属于这三类的
  内部符号不进包导出面。
- **测试从产物入口导入 = 把内部符号钉死在公共 API 上**。测试应白盒直连 `src`，
  契约测试才经入口/出口，集成测试才经产物。
  *案例*：某包运行时导出 72 个符号，其中 43 个仅被测试从产物导入，
  而唯一跨包消费者是经服务面消费、零 import。
- **注入面收窄三手段**：`Pick` 收窄、Ports 注入、装配-消费分离。
  *案例*：把「继承上游端口类型」改成「只声明本域真正需要的几个能力」，
  下游实现方无需知道上游的形状。
- **裸漏形状是耦合来源**：以 `Record<string, unknown>` 或 `any` 出现在跨域签名上的
  数据结构，等于没有契约。
  *案例*：线协议帧的生产端返回宽泛记录、消费端收 `any`，字段改名不会有任何门禁报警。

## 7. 依赖事实图 × 意图图

- **事实图**：脚本从源码实测的依赖边（值 / 类型双构、扇入扇出、值环清单）。
- **意图图**：各域 `deps.ts` 手写的「本域依赖谁的什么能力」。
- 两图对照产出：**泄漏面**（事实有而意图无）与**死声明**（意图有而事实无）。
- 粒度纪律：**叶子粒度**建图；分组层透明。
  *案例*：顶层粒度让一个包丢掉 27 条边、另一个包丢掉 115 条边，
  其"域级值依赖边 1 条"是假象。
- 约束：意图图必须保鲜（泄漏面计数判红），否则会单调腐化。

## 8. 测试三层与导入面矩阵

分层不能只靠文件名前缀，必须由**导入面**定义并可机器校验：

| 层 | 只允许 import | 测什么 | 替身 |
|---|---|---|---|
| 单元 | `src/<域>/<impl>.ts`（同域） | 模块内函数与状态机（白盒） | 零替身 |
| 契约 | `src/<域>/interface.ts`（入口）+ `src/<域>/deps.ts`（出口）+ 跨端线协议 | 只测接缝的形状与承诺，不测实现细节 | 入口本身即注入面，可用 fake |
| 集成 | 包产物入口 + `apply()` | 端到端 user case | 仅系统边界（网络、子进程、临时目录、时钟） |

配套纪律：

- **度量完整性**：每个 `src` 文件必须可被覆盖率与变异面覆盖，否则等于新造零度量面。
  新增源文件时同步登记归属。
- **测试卫生**：孤儿测试检测、冗余断言合并、恒真断言（只断言"不抛错"）改写、
  静态文本哨兵限额（对源码文本的 `includes` 断言应限于真实 ABI 与安全约束）。
- **假绿向量必须显式封堵**：零匹配、零断言、`exit(0)` 吞失败——三者都会让
  "绿灯"失去意义。

## 9. 门禁工程

- **左移阶梯**：脚本门禁（并入既有 contract 段）→ 编辑器内联提示（可选，需评估
  新增依赖的真实收益）。*案例*：全量门禁已在本机 1.5 秒内跑完，"本地秒级"不构成
  引入整套 lint 工具链的理由；编辑器反馈是其唯一独占收益。
- **单调基线**：每包每类计数只许降不许升，基线文件入库。
- **执法点只有一个**：新增门禁必须挂到既有 CI 步骤（如 contract 段），
  不要新增工作流——那是更高层级的变更。
- **门禁自测**：用 fixture 做正反双向断言（违规判红、合规判绿），
  不要只依赖真实包跑出 PASS。
- **禁止双轨**：同一约束不要同时由两个工具强制，否则口径漂移无法裁决。
- **判据的自述必须与实现同源**：门禁打印的每个数字都要能被一条命令复核，且「与基线
  一致」这类声称必须与前件绑定；否则门禁自己就制造假绿（声称一致时读的却是另一个量）。
  *案例*：`export-surface-snapshot --verbose` 曾打印**当前**声明块数（105）并称「与基线
  一致」（基线 96）——两个计数本就不同源（比对只取导出面符号的定义块）。#733 M2c 改为
  分列「当前 / 基线」并把「一致」的声称与两者相等绑定，配端到端自测。
- **「门禁看不见什么」要实测成矩阵，不能靠读代码推断**：对每一类符号变更各做一次真实
  改动，逐个跑全部门禁，红/绿逐格记录——覆盖表的价值在于**空格**。
  *案例*：#733 M2c 对三类符号各做一次签名变更（值面签名 / interface 体 / 域内非导出面
  符号）：值面 → 快照门禁红、其余三绿；interface 体 → 快照门禁**绿**（`export interface`
  无 `declare`，连提取器都进不去），由消费方类型体锚判红；域内非导出面符号 → **四条
  门禁全绿**。第三格是「另开判据」的输入，不是「无须治理」的证据。
  随后一轮**对抗性复核**又把第二格拆细：同一次实测发现「包导出面的值面签名」并非总是红
  ——同名多块时只比对排序末块，包入口 `apply` 的签名改写实测 **exit=0**（改客户端块才红），
  且导出面里 32 个名字两侧都无声明块（含 4 个 re-export 值符号）被静默跳过。**结论**：
  一次矩阵只覆盖你想到的类目；「看不见什么」必须由**独立复核去证伪**，而不是由作者自证。
- **矩阵的每一格都要能被一条命令推翻**：格子的结论若写成「X 类改动会红」，就要能拿出
  一次真实改动 + 真实 exit code；否则它只是作者的印象。
  *案例*：上条「值面签名 → 红」在 `formatDuration` 上成立、在 `apply` 上不成立——
  同一个「类」内部就有反例，故矩阵要落到**具体符号**而不止于类目。

## 10. 口径与证据纪律

- **存量数字四要素**：commit + 脚本 + 粒度 + 计数单位，缺一不可。
  *案例*：某 issue 的存量数字取自两个月前的中间提交，照单执行会去做一件
  已经被完成的事（值环已为 0）。
- **区分「约束收紧后的存量」与「既有缺陷」**：前者是治理成本，后者才需要修。
  *案例*：39 处、91 处、155 处存量的目标全部是"他域公开门面"，在旧规则下
  100% 合法。
- **P0/P1 断言必须实测**，不接受纯代码推理定性；**子 Agent 结论必须交叉复核**。
  *案例*：一次评审中 4 条来自子代理的"必须修"结论经复核被否决或降级
  （会重现值环的落点建议、触发路径不成立的冲突、与真实产物形态不符的基线判断、
  被误判为单包独有的跨包一致模式）。
- **区分文档承诺与实现**：注释与文档中的"宁可归零不可卡死"这类承诺，
  必须有一侧被机器锁定，否则会长期反向。

## 11. 实施流程

```
issue 回填与批准 → 门禁尺子 → 度量修复 → 真缺陷 → 契约与共享层 → 结构分层 → 接口深化 → 测试重构
```

- **每阶段单 PR、可独立回滚**；仓库级改动与包级改动分轨。
  *案例*：为一个包修覆盖率而改动 6 个包共用的构建脚本，违反可回滚纪律，
  应改为复用既有 hook 的 1 行方案。
- **零行为变更由导出面快照证明**：导出符号集合 + 声明块多重集；
  该证据对文件搬移免疫、对定义改写敏感，是结构重构唯一可靠的"没有破坏"证明。
- **公共 API 行为变更、新增依赖、工作流与发布变更**按仓库红线先评审。
- 收尾在 PR 描述里逐条粘贴实际 exit code，不粘贴就不得声称完成。

## 12. 维护期检查清单

> 落地要求：清单若只停留在文档里，就违反了第 1 章第 4 条原则（未被机器强制的约束
> 等于不存在）。它应当挂进 PR 模板与开发 skill 的执行步骤，使每次改动都被实际过一遍。

改动前：

- [ ] 这个符号有明确的领域所有者吗？我是在「依赖」它还是在「共享」它？
- [ ] 这次消费是合理的吗，还是我在图方便、绕过了应有的注入？
- [ ] 门禁能看见我改的这个地方吗？（粒度、扫描面、豁免面）
- [ ] 我新增的文件会被覆盖率与变异面覆盖吗？
- [ ] 新增一项要改几处？超过 3 处就先重构扩展点。

改动后：

- [ ] 导出面快照是否有预期内的 diff？基线更新是否显式且说明理由？
- [ ] 覆盖率与变异面是否缩水？新出现的未覆盖文件是否有正当理由？
- [ ] 是否引入了新的假绿向量（零匹配、零断言、吞失败）？
- [ ] 存量数字是否带齐四要素？
- [ ] 文档（含双语 README、规范、skill）是否与实现同 PR 同步？
