# 模块架构梳理·讨论·决策·TDD 重构工作流（通用方法论，人在环驱动）

> 用途：对仓库内任一模块（`{MODULE}`）执行一次「全量功能特性与需求规格梳理 → 分层架构讨论与
> 层边界裁定 → 架构图可视化 → 决策拍板 → 对抗性评审收敛 → TDD 重构方案」的完整闭环。
> 本方法论为**通用版**：不绑定任何具体模块的业务细节；各环节以代码事实为证据、以人为裁决。
> 使用方式：替换 `{占位符}` 后作为任务 Prompt 交给 agent；按 §0 红线与 §2 人在环约定执行。

---

## 0. 任务前红线检查（不满足不开始）

- [ ] 任务从仓库 issue 派生（无 issue 先建/认领；方案性改动先在原 issue 起草
      `needs-proposal-review` 方案评论，获维护者 `approved` 后动手）。
- [ ] 主 checkout 保持干净：**只在独立 worktree**（`git worktree add ../dsh-hub-task-<n> -b task/<n>`）
      内改代码/构建/测试/归档；禁止在主 checkout 改代码、跑实验。
- [ ] 绝不动宿主源码、绝不重启/杀宿主服务进程（红线）。
- [ ] 全中文表达（代码/专有名词/协议名保留原文）；安全语义变更（凭据/执行/令牌/外部可达面）
      必须显式声明并走红线流程。
- [ ] 定位 `{PKG_DIR}=packages/{MODULE}/`；先通读包 README（中英）、package.json、
      挂载配置（cordis.patch.yml 等）、docs/、近期提交记录（修复/遗留线索）。

## 1. 全量功能特性与需求规格梳理（产出规格章）

1. **特性清单化**：按域枚举功能特性，编号 `F<域>-<序>`；每条 = 行为描述 + 实现位置（文件:行号）
   + 需求来源（文档原文 / issue 号）。逐条覆盖：配置与持久化、运行时生命周期、对外接口面、
   客户端交互面、观测与诊断、跨模块契约。
2. **规则化**：把文档/代码语义转成「可测试的需求规则」，每域给「happy / 边界 / 异常 / 并发竞态 /
   安全」五行矩阵——作为后续 TDD 用例矩阵的输入。
3. **覆盖全读**：宿主端 `src/` 全量（入口导出面、装配层、路由、存储、协议、生命周期）→
   客户端 `src/client/` 全量 → 仓库共享层中本模块消费面 → `test/` 全量（运行模型、断言强度、
   执行矩阵）→ 变更历史。
4. **本环节产出**：规格章初稿。**→ 人在环检查点 G1（见 §2）：呈现用户审阅规格与覆盖结论，
   确认无遗漏后再进入分层讨论。**

## 2. 分层架构讨论与层边界裁定（人在环核心）

### 2.1 人在环约定（全程生效）
- **分工**：agent 负责证据收集、草案、对比与过滤（把已过滤掉大部分错误的结果呈现给用户）；
  **人负责方向、取舍、红线与批准**。
- **强制检查点（present-gate）**：每个阶段产出后必须呈现给用户确认，**未经确认不得越过阶段**；
  用户可随时中止、改向或追加约束。
- **决策表**：所有取舍项（拆分/合并/新增/维持、公共面变更、安全语义、门禁策略）进编号决策表
  `D1..Dn`（选项 + 推荐 + 技术依据），**由用户拍板**后才进入实施路径。

### 2.2 层边界裁定（证据驱动，不文档主义）
- 若用户给出候选层清单：先把模块精确映射进每层；再裁定：
  - **可拆**：单文件行数/职责混叠显著、同类缺陷跨子域归因（如「编排 vs 执行」混层）
  - **可合**：纯逻辑与 IO 已分文件却仍算两层的「贴标签」
  - **新增横切层**：被多处消费且有真实缺陷的「单一事实源」候选（路由解析、状态事件、执行管道…）
  - **维持**：边界清晰的既有层
- 裁定必须落到代码证据（行数、依赖方向、缺陷归因），并在讨论中向用户呈现「拆/合/增/维持」表。

### 2.3 架构图可视化（archify，独立环节）
- **何时画**：
  - 分层裁定定稿后 → 画「现状分层架构图」（讨论载体，帮助人与评审对齐层边界）；
  - 重构方案定稿后 → 画「目标分层架构图」（含目录/契约/依赖方向），可与现状图对照评审；
  - 层边界有争议时 → 用图聚焦争议区域。
- **画什么**：分层图（组件=层或域、边界=进程/端、连线=层间契约依赖、卡片=职责/规则/风险）；
  聚焦视图表达主链路/横切面/装配时序；可选序列图表达关键流程（会话切换、调用执行链）。
- **验收闭环**：候选 JSON → `validate`（目标质量档 9/9 零错零警）→ `deliver`（冻结规格快照）→
  `visual-check`（多视口无溢出、明暗主题、截图证据）→ **图呈现给用户与评审代理**。
- **几何调优经验**：标签重叠优先按 validate 建议的 labelAt/labelDy；纵向溢出优先压缩行距/节点高/
  卡片文本而非放大显式 viewBox；连线穿节点优先调整端口侧（fromSide/toSide）与节点位置，
  低价值边可删除改由卡片说明。
- **→ 人在环检查点 G2：用户基于现状图确认层裁定，再进入缺陷识别。**

## 3. 缺陷全量识别与测试盲区交叉验证（产出缺陷清单章）

1. **规格-实现对照**：逐条需求规则 vs 实现找偏差；对照文档承诺的数值/语义（状态分级、超时、
   截断、脱敏、重连预算、幂等性等）。
2. **对外交互面契约核对**：客户端/外部消费方与宿主接口逐项核对（请求形态、响应契约、帧协议、
   幂等性、参数完备性、错误语义）。
3. **测试盲区交叉验证**：对每个嫌疑缺陷用检索验证「现有测试是否真的覆盖」——缺陷常藏在：
   - 测试只断言状态机末端、未断言中间过渡态；
   - 测试文件是执行矩阵孤儿（不在主入口 import、不在变异执行清单、不在拓扑登记——三处任一缺失）。
   输出：严重度 P0/P1/P2/P3 + 位置 + 与规格偏差 + 覆盖盲区占比。
4. **防伪证**：每条结论附代码检索证据（文件:行号），不靠印象。

## 4. 决策拍板（产出规格决策表）

- 每个「或规格化声明」项、公共面（命名/公开 API/安全语义/门禁）修复方向，进决策表
  `D1..Dn`：选项 + 推荐 + 技术依据（引代码行）。
- **防伪决策**：任何「改动面很大/很小」的判断先用检索验证（如 grep 调用方、读门禁实际判分逻辑），
  再进决策表；不基于印象拍板。
- 涉及门禁/基线的决策（判分口径、迁移豁免）先读仓库 `scripts/gate/*` 与基线配置的**实际判分
  逻辑**，不停留在「需澄清」。
- **→ 人在环检查点 G3：用户拍板决策表全部 D 项后，才允许进入重构方案。**

## 5. TDD 重构方案（产出 TDD 计划章）

1. **红测清单**：每个已确认缺陷一条红测，标注：可测性（纯函数/状态机 mock/集成桩）+ 前置依赖
   （测试接线、契约先决）+ 断言点建议（避免整窗口轮询、避免读私有字段——优先纯函数断言）。
2. **需求规则矩阵**：§1 矩阵展开为用例清单，顺序：纯函数层（无副作用，红绿最快）→ 状态机层
   （mock 传输/协议桩统一进测试辅助）→ 集成/契约层（路由围栏、事件推送、服务契约、客户端契约）
   → 客户端 UI（隔离浏览器实测，不入单测门禁）。
3. **分阶段**：阶段 0 契约冻结/规格决策 → 纯函数 → 状态机 → 集成 → 集中式纯搬移（如需要）→
   客户端 → 质量收口；每阶段独立 PR 关联同一 issue；每阶段末全绿门禁 + 修复/收敛分 commit。
4. **静态面普查**（搬迁/目录化前必须做，否则必红）：
   - 测试按「源文本路径」的静态扫描（被扫描文件在集中迁移前**禁止移动/薄转发**）；
   - 变异测试各段 `mutate` 为显式文件清单，与拓扑/断言门禁三方一致；基线为源码口径；
   - 新建文件不挂任何段 = 变异盲区（防空段断言不查全覆盖）——「逐阶段挂段 vs 集中重画」拍死并明示；
   - 客户端构建入口文件是产物契约锚点，保留；资源相对引用路径随迁移变化；
   - 集中迁移 PR 验收三件套：迁移前基线快照全绿 / `git diff --stat` 纯移动零行为变更 /
     迁移后全绿 + 基线重建豁免机制。
5. **测试纪律**：临时目录隔离落盘；事件驱动/轮询替代固定 sleep；测试单份维护（产物 + 变异复用
   同一断言）；新测试文件必须主入口 + 变异清单双登记。
6. **→ 人在环检查点 G4：用户批准 TDD 计划与分阶段顺序后，进入对抗性评审。**

## 6. 对抗性评审（多轮收敛，人在环裁决）

1. **独立子代理**（后台，prompt 自包含：文档路径 + 代码事实源 + 仓库约束 + 评审维度）；
   评审维度：正确性/边界、性能与资源、安全、可维护性、兼容性（主题/端/平台）、与既有约定冲突、
   过度设计。
2. **评分制**：<70 需重大修正；70–85 机制空洞需补（方向对、机制缺）；≥90 可进 issue 方案评审。
3. **每轮评审后**：归档纪要（总评、逐维度发现、裁定表、缺口清单、P0/P1/P2 修正）；修订方案版本
   （v1→v2→…）；逐条核对 A 表（上轮 P0/P1/P2 → 本轮落实 ✅/⚠️/❌）。
4. **评审的评审（C 复核）**：倾向上轮评审自身的误判（过时事实、失实涟漪、过强后果），撤回/修正
   落到新代码证据。
5. **人在环检查点 G5（每轮必过）**：把评审纪要（含 A 表与修正建议）**过滤后呈现用户**，由用户
   裁决：接受修正方向 / 驳回某项 / 追加约束；**未经用户确认不进入下一轮或实施**。
6. 收敛标准：连续两轮无新 P0 + 评分 ≥90（或评审明确「可执行」）**且用户确认收口**。
7. 子代理协作经验：prompt 要求「第一条回复即完整报告正文」（否则常只回摘要）；后台运行时完成
   后通知父代理，需追全文用消息指令。

## 7. 归档与产出物清单（进 worktree 分支提交）

- `docs/requirements-and-tdd-plan.md`：需求规格（F 编号 + 规则矩阵）+ 缺陷清单（分级 + 证据 +
  测试盲区）+ 测试审计（执行矩阵/哑断言/脆弱点）+ 分层架构 + TDD 计划 + 评审纪要（可拆多文件）。
- `docs/architecture-redesign.md`（v<N>）：目标分层/契约/目录/迁移策略/阶段计划/决策表 D1..Dn。
- `docs/architecture-redesign-review.md`：各轮对抗评审纪要（评分、A 核验表、B 新问题、C 复核、
  人在环裁决记录）。
- `docs/diagrams/`：archify 现状/目标 JSON + HTML + visual-check 证据。
- 评审通过且用户确认后：建 issue 方案评论（决策表 + 契约缺口清单 + 迁移门禁策略三件套）→
  worktree 开发 → 分阶段 PR → 门禁全绿 → squash merge。

## 8. 完成定义（Definition of Done）

- [ ] 规格/契约/决策三件文档齐全；评审 ≥90（或明确可执行）**且经用户在环确认**（G1–G5 全过）
- [ ] 全部 P0 缺陷有红测且修复后变绿；P1 按阶段计划排期
- [ ] 构建/测试/契约/打包/类型检查全绿；变异与覆盖率守基线判据；无新增哑断言/固定 sleep
- [ ] 涉及公共面/安全语义的变更已过红线并同步文档
- [ ] 产出物全部归档在 worktree 分支，主 checkout 零改动
