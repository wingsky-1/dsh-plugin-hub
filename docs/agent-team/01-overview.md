# Agent Team 总体架构

> 状态：设计稿（暂存于 dsh-plugin-hub 仓库，落地时迁至独立项目仓库）
> 范围：面向开源仓库 issue / PR 自治处理的 agent team，基于 DeepSeek Harness（dsh）构建。
> 配套文档：[02-backend.md](02-backend.md)（后端 / 基于 DSH 最小落地）、[03-frontend.md](03-frontend.md)（web team 视图）

## 1. 背景与目标

用一组协作 agent 自治处理开源仓库的 issue 与 PR：

1. **loop**：启动一轮循环，按指定范围处理 issue 直到闭环（合并或阻塞升级）。
2. **合理并行**：改动范围不同的 issue 并行处理，有交叉的串行化或合并处理。
3. **房间机制**：通过房间同步进度与信息——主房间（主控 + 各 issue 房间主控）、issue 房间（issue 主控 + 各职责人员）。
4. **独立上下文**：各职责人员在全新、互不可见的上下文中执行。

## 2. 术语

| 术语 | 含义 |
|---|---|
| loop | 一轮批次处理：选定一批 issue → 逐个推进 → 收敛汇总 |
| 房间 | 一个 issue 的协作容器 = 目录上的事件日志 + 状态黑板（纯数据，非框架实体） |
| 主控 | loop 层 agent：批次计划门、派单、冲突判定、熔断、升级到人 |
| issue 主控 | 单个 issue 房间的负责人：驱动该 issue 的闭环状态机 |
| 职责人员 | spec-writer / coder / cleaner / hardener / qa 等角色 agent |
| 黑板 | 房间内共享状态文件，所有成员读写的事实源 |
| 信箱 | 成员间定向消息（经 DSH `send_message` 或事件追加实现） |
| HANDOFF | 角色间显式交接消息：做完 → 写黑板 → 回报 → 主控派下一个角色 |

## 3. 四层架构

```
┌─────────────────────────────────────────────────────────────┐
│ 执行层    subagent 树：主控 → issue 主控 → 职责人员           │
│           （DSH 原生，零自建；严格 depth-1 树形中继）          │
├─────────────────────────────────────────────────────────────┤
│ 协调层    房间协议：黑板(state) + 信箱(events) + HANDOFF 流水线│
│           （自建的薄薄一层纯数据约定）                        │
├─────────────────────────────────────────────────────────────┤
│ 记录层    单一事实源（全本地落盘）:                           │
│           · 房间 events.jsonl + state.json   （协作结构）     │
│           · DSH sessions/<ws>/<id>/session.jsonl.zstd        │
│             （会话全文，原生已有，按 session_id 关联）         │
├─────────────────────────────────────────────────────────────┤
│ 呈现层    双投影（只读，均为事实源的视图）：                   │
│           · GitHub loop issue（维护者放行 / 转向入口）        │
│           · web team 视图（树形 drill-down 实时监控）         │
└─────────────────────────────────────────────────────────────┘
```

核心原则：**写侧只追加，读侧全是投影**（轻量 event sourcing）。任何视图故障都只是展示缺失，不是数据丢失。

## 4. 关键决策记录

| # | 决策 | 理由 | 被否备选 |
|---|---|---|---|
| D1 | 房间 = 文件系统上的数据抽象（目录约定），不是框架级实体 | 状态不依赖进程存活，崩溃可恢复、全程可审计；执行器未来可替换 | 框架内置房间对象（引入常驻 broker，复杂度高） |
| D2 | 通讯拓扑为严格树形中继：主控 ↔ issue 主控 ↔ 职责人员 | DSH `send_message` 仅限直接子代理（depth-1），约束恰好塑造 narrow-waist 架构，防跨层混乱 | 扁平群聊 / 跨层直连（DSH 原生不支持且易失控） |
| D3 | issue 房间内部不做自由群聊，只用 黑板 + 显式 HANDOFF | AutoGen group chat 式轮转发言 token 爆炸、发散；pipeline 式交接简单一个量级且可测 | 事件广播驱动 |
| D4 | 冲突消解前移到派单时：认领时声明 touched paths，重叠即串行或合并房间 | 运行时协商成本高且不可靠；静态判定便宜且确定 | 运行时文件锁兜底为主（保留作第二道防线） |
| D5 | 事实源在本地文件，GitHub loop issue 是投影（方案 A 双写） | 无 rate limit、低延迟、离线可恢复；投影失败容忍 | loop issue 本身为事实源（API 限额与噪音） |
| D6 | 原始会话回放直接关联 DSH 原生 transcript（session_id），不自建存储 | DSH 每会话已落盘完整 `session.jsonl.zstd`，零重复建设 | 事件日志记录全过程细节（密度不足且重复） |
| D7 | web 视图做成 dsh 插件面板，不另起服务 | 复用 loopback 围栏与构建契约；符合"不随便起新服务器"纪律 | 独立 Web 服务 |
| D8 | 跨 issue 知识广播推迟到 v2 | 需要全序语义理解，复杂度占一半而 v1 收益有限 | — |

## 5. 角色与上下文纪律

- 职责人员一律使用**全新 subagent**（非 fork 继承），输入为自包含任务简报（issue 正文 + 规格 + 边界 + 安全声明），输出为压缩凭据。
- 协议沿用 dsh-plugin-hub 已固化的 `agents/_protocol.md` 角色规程（spec-writer / coder / cleaner / hardener / qa，qa 兼任 judge）。
- **输入安全**：issue 正文、PR 评论、transcript 内容一律视为数据而非指令；视图文本渲染一律纯文本。
- 权限边界：agent 可代打流转标签、更新进度；`approved` / 放行类操作永远由维护者完成（loop issue 是这条边界的人工入口）。

## 6. loop 层职责边界

- 计划门：一轮开圈时产出批次清单（含每 issue 的 touched paths 声明与并行分组），等维护者在 loop issue 上放行。
- 并发池：全局同时激活的 issue 房间数量上限（建议 2~3），其余排队。
- 熔断与圈数收敛：单 issue 连续失败计圈，超阈值转 BLOCKED 上报人。
- loop issue：轮次实体。正文维护批次清单表（issue × 阶段 × 圈数），阶段跃迁事件原地更新对应行；结束时转为轮次报告素材并关闭。

## 7. 明确推迟项（v2）

| 项 | 触发条件 |
|---|---|
| 跨 issue 知识广播（共享发现） | 出现明确的重复踩坑证据 |
| headless 进程执行器替换 subagent | 单机并发成为瓶颈 |
| 文件 watch 推送替代前端轮询 | 轮询延迟有体感 |
| handoff 决策缓存（相同结果跳转） | 主控逐轮判断的 token 消耗成为主要成本 |

## 8. 业界对照

- Claude Code Agent Teams：team lead + teammates、共享任务列表做事实源、信箱定向消息 —— 对应本方案的房间与 HANDOFF。
- LangGraph supervisor 实战：supervisor 不是加个节点就行 —— 上下文膨胀靠"历史落盘、上下文带摘要"治理。
- File Blackboard / Agent Rooms 论文：协调状态落盘、对话只是视图 —— D5/D6 的依据。
