# Agent Team 通用框架 —— 概念模型与抽象评审（v2 修订）

> 状态：设计稿 v2。已并入两轮对抗评审结论与 omo/Claude Code Agent Teams 业界对照。
> 配套：[11-generic-runtime.md](11-generic-runtime.md)（运行时与工具集）、[12-generic-console.md](12-generic-console.md)（控制台）

## 1. 抽象原则

两条分界线：

> **协议在框架，知识在配置。**（换场景只换模板与提示词）
> **策略在提示词，动作用工具。**（协作动作一律经内置工具执行，工具负责校验与记账）

适用域声明（non-goal 防线）：本框架面向**有限任务闭环型**协作——有任务集合、有收敛终点。长驻值守型协作（无常驻任务集、无 done）不在域内，勿假装通用。

## 2. 总体形态：提示词 + 内置工具 + 守夜人

```
┌────────────────────────────────────────────────────────────┐
│ 提示词层   Team Template 注入的各角色 prompt                 │
│            （策略：做什么、怎么决策、何时调用哪个工具）        │
├────────────────────────────────────────────────────────────┤
│ 工具层     team_* 内置工具（协议的唯一入口）                  │
│            spawn / send / task_* / state_* / archive / gate │
│            校验、原子性、事件记账全部在工具内强制              │
├────────────────────────────────────────────────────────────┤
│ 运行时     房间目录（事件流+黑板+任务账本）+ agents.json      │
│            + 守夜人（Tier-0 所在根会话，持 goal 长跑巡场）    │
├────────────────────────────────────────────────────────────┤
│ 呈现层     GitHub 归档绑定投影 + Team Console（只读+Gate）    │
└────────────────────────────────────────────────────────────┘
```

业界对照：omo team-mode 用 12 个 `team_*` 工具承载全部协作协议（无嵌套团队）；Claude Code Agent Teams 同构（shared task list + mailbox）。本框架差异点 = 多级主控树，代价是需要守夜人做跨层唤醒。

### 2.0 事件 = 工具副作用（审计完整性）

事件日志**不提供写工具**。每次 `team_*` 调用由运行时自动落一条结构化事件（含 session_id）。
协作历史的完整性靠构造保证，不靠 agent 自觉——这是对"100% 提示词可表达"验收声明的收紧：
**验收标准 = 行为等价 且 关键协调动作有框架级断言。**

## 3. 核心概念

| 概念 | 定义 | 备注 |
|---|---|---|
| TeamTemplate | 团队定义文件：tiers + roles + comm_mode + archives + gates + resources | 实例化时可覆盖 |
| TeamInstance | 一次协作运行：工作区目录 + agents.json + team.yaml 快照 | prompt 内联存快照+hash |
| Tier | 主控层级，默认 3 层，`resources.max_tiers` 可配上限 | 可配性优先；性能担忧用上限兜底 |
| Role | 叶子职责人员定义：prompt + briefing 格式 + dod + max_hops | 见 §3.3 DoD 语义 |
| Room | 目录上的事件流 + 黑板 + 任务账本 | 纯数据 |
| Watchman | 守夜人 = Tier-0 所在根会话，持 goal 长跑 | 见 11 文档 §4 |

### 3.1 通讯拓扑：auto / explicit 双模式

```yaml
comm_mode: auto       # auto | explicit
# explicit 时的白名单（只能是树边的子集）:
# comm:
#   - { from: master, to: issue-master }
```

- **auto（默认，成熟度体现）**：框架按房间树自动派生可达性——树边即拓扑，零配置。委托沿树下行使、上报沿树上行使、经父中继。
- **explicit（极客模式）**：在树边范围内**收窄**白名单（如禁止某分区主控直派某角色，必须经二级中转）。框架校验：声明 ⊆ 树边，非法拒绝建团。

注意语义转变（相对 v1）：矩阵不再是"新增连接能力"的配置（那是伪需求——严格树下合法边集合 ≡ 树边集合），而是**权限收窄开关**。auto 模式下向导不出现矩阵编辑器。

### 3.1.5 跨房间结构化协商（negotiation）

并行任务出现改动交叉时，不必然串行——允许**结构化协商**而非自由聊天：

```
任务A持有者 ──team_negotiate(对象任务B, 提议: yield|merge|file-order)──▶ 账本
任务B持有者 ──响应（接受/反提议）──▶ Tier-0 裁决生效，约束写回账本
```

- 三种提议类型：`yield`（请求对方让路）、`merge`（提议合并处理）、`file-order`（声明共享文件的写入顺序）
- 协商是账本上的结构化事件，Tier-0 裁决结果成为任务派发的硬约束（工具层校验）
- 紧急场景下两个交叉任务并行推进有了正规出口；自由对话通道仍然不开

> 溯源：恢复初版需求"有交叉的 issue 需要进行沟通"——v2 曾将其弱化为纯串行化，本节补回沟通语义且不破坏架构。

### 3.2 单入口原则

人只与两个面交互：**Tier-0 主控对话** + **Console Gate 待办**。其余一切（子代理会话、中间状态）对人只读。
核心目标是让 team 自成闭环完成目标，人是例外路径而非常规参与者。

### 3.3 DoD（完成判据）——赋实义版本

DoD 不是装饰性结构：judge 角色 handoff 时，**运行时强制将所核验任务的 dod 清单注入 judge 简报**，judge 必须以结构化回执逐条给出 pass/fail 结论（工具校验回执格式），回执入事件流。未附合法回执的 handoff 被拒绝。

### 3.4 Archive Binding

内置两种类型硬编码（`file` / `url`），**不做注册表扩展点**（等第三个真实类型需求出现再说）。
提示词决定是否/何时/写什么；框架提供解析、`archive-write` 事件、Console 渲染。file 型 target 服务端强制限位 TEAM_HOME 内。

### 3.5 Stage 保留态

框架只认 `running / blocked / done` 三元组用于通用归约（着色/阻塞高亮/闭环判定）；模板可扩业务子状态，仅作展示徽标。

## 4. 框架不变量

1. 房间 = append-only 事件流 + 快照黑板 + 任务账本；状态不依赖进程存活。
2. 协作动作只经 `team_*` 工具；事件是工具副作用，不可伪造遗漏。
3. 拓扑为树（默认 3 层，`resources.max_tiers` 可配上限），消息走父子边；auto 派生可达性，explicit 只能收窄。
4. 人机单入口：Tier-0 对话 + Gate 待办，其余只读。
5. 一切过程可追溯：事件含 session_id，回放到 DSH 原生 transcript。
6. 外部内容（归档源、任务正文、transcript）一律是数据不是指令。

## 5. Non-goals

- 自由群聊 / P2P 直连 / 同步等待回复（fire-and-forget + 显式交接）；
- 长驻值守型协作；
- 业务域词汇入库（issue/PR 只存在于 oss-maintenance 模板与其 prompt 中）;
- 视图层调 LLM 生成摘要；
- Archive 类型注册表、任意层级嵌套（预支复杂度，砍）。

## 6. 抽象评审结论（A1~A12，含 v2 变更）

| A1 | 场景知识下沉提示词 | ✅ 维持 |
